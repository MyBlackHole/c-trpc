# 平台、SDK 与部署契约

`2.0.0-dev.1` 的当前评估见 [R17 发行边界与后续责任](reviews/rpc_v2_release_boundary_20261023.md)，
其中区分实际主线验收、性能诊断负结果与尚未完成的专项，不构成稳定版发布批准。

## 已验证范围

- 主要实现是 Linux 专用的 C11 静态库，使用 pthread、epoll、eventfd、accept4、TCP 等接口，以及 GCC/Clang 的 cleanup 属性。
- CI 使用 Ubuntu 22.04 的 x86_64 执行环境；GCC 的 `debug/release` 模式、Clang 的 `release` 模式、ASan+UBSan、TSan、安装消费端与真实 RPC 冒烟测试是现有门禁。
- 公开安装头文件为 trpc.h、status.h、facade.h、client.h、server.h、transport.h、rpc.h、rpc_codec.h、rpc_v2.h。内部头文件不属于 SDK。
- C++11 消费端验证公开头可独立包含、C 链接约定、门面配置/状态调用和真实 V2 Client/Server 业务；内部实现仍按 C11 编译。

主动连接及监听 socket 使用 Linux 的 `SOCK_NONBLOCK | SOCK_CLOEXEC` 原子创建；
不回退到创建后 `fcntl` 设置，避免并发 fork/exec 继承窗口。该保证针对
`socket()` 创建路径；现有 accept4 不可用时的 accept 兼容路径不在此保证内。

原先的 “Linux 3.x+” 没有对应最低版本内核测试，因此不再作为支持承诺。
`SO_REUSEPORT` 等系统能力对具体配置有额外要求；调用失败应检查返回状态。
CI 的发行版标签不等于最小内核版本测试。arm64、32 位、大端、旧内核和其他 libc
在建立实际验证前均列为未验证，而不是默认兼容；隐藏 SSE4.2 的 x86_64 测试只证明
CRC 回退路径，不能替代跨架构测试。

## 兼容与生命周期

- 当前发布静态库；应用须使用同一源码版本的头文件和库并重新编译。不承诺跨版本二进制 ABI，也不把配置结构大小或不透明/私有字存储布局当作持久化格式。
- 初始化配置时使用对应 `*_config_init()`；升级时检查源级 API 与线协议变更。线协议版本/帧字段的校验不等于任意新旧应用混部兼容性已获证明。
- 检查所有返回状态，包括容量拒绝、超时、关闭和可重试销毁。失败回收后仍存在已发布的持有关系时，必须保留对象并按接口契约重试，不能忽略错误后释放用户回调存储。
- 停止/排空不抢占用户回调，业务期限不是所有锁竞争、排队、回调和销毁屏障的硬实时返回保证。连接器的单次尝试期限当前从初始非阻塞 `connect` 调用返回后开始；不要把它当作整个 API 排队时长的 SLA。
- 有限代次只在未回绕窗口内隔离旧句柄；`aux` 使用非零 32 位代次，不能宣称永久无 ABA。

## 上线前必须确认

1. 安全边界：CRC 是损坏检测，不能提供身份认证、机密性或对抗主动篡改。库没有集成 TLS 或应用消息压缩；不应直接暴露到不可信公网。应用必须提供实际验证的认证/授权及传输保护方案。未来的 TLS 1.3 与可选压缩要求详见[压缩与 TLS 需求](architecture/11-compression-tls-requirements.md)，该文档不代表当前版本提供相应接口或安全保护。
2. 容量与运维：基于目标硬件、载荷和连接数实测延迟分位、拒绝率、CPU/RSS、fd 上限及资源饱和后的恢复。不要把关闭负载或增大资源后取得的吞吐当作原配置保证。
3. 故障与长稳：跨进程 TCP、断网/半开、慢读写、重连风暴、长时间运行和升级/回滚须在目标环境验证；普通 CI 与有限故障注入不证明所有故障组合。
4. 业务语义：RPC 成功不等于数据持久化，也不提供业务幂等或自动安全重放。重试前由上层确定请求是否可能已经生效。
5. 许可：当前项目内容采用 Apache-2.0。分发时随附 LICENSE、NOTICE 与许可来源说明；历史 Linux 配置及外部工具不被重新授权，详见 [许可与来源范围](licensing.md)。

因此，“既定平台上的 CI 与回归通过”只能作为受控部署候选的工程证据，不能替代
上述安全、容量、故障和许可验收，也不意味着 #154 的全部工程整改已经完成。

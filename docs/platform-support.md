# 平台、SDK 与部署契约

## 已验证范围

- 主要实现是 Linux 专用的 C11 静态库，使用 pthread、epoll、eventfd、accept4、TCP 等接口，以及 GCC/Clang 的 cleanup 属性。
- CI 使用 Ubuntu 22.04 的 x86_64 runner；GCC debug/release、Clang release、ASan+UBSan、TSan、安装消费端与真实 RPC smoke 是现有门禁。
- 公开安装头文件为 trpc.h、status.h、facade.h、client.h、server.h、transport.h、rpc.h、rpc_codec.h。内部头文件不属于 SDK。
- C++11 消费端仅验证公开头可独立包含、C linkage 和门面配置/状态调用，不承诺内部 C 实现可按 C++ 编译。

原先的 “Linux 3.x+” 没有对应最低版本内核测试，因此不再作为支持承诺。
`SO_REUSEPORT` 等系统能力对具体配置有额外要求；调用失败应检查返回状态。
CI 的发行版标签不等于最小内核版本测试。arm64、32 位、大端、旧内核和其他 libc
在建立实际验证前均列为未验证，而不是默认兼容；隐藏 SSE4.2 的 x86_64 测试只证明
CRC fallback，不能替代跨架构测试。

## 兼容与生命周期

- 当前发布静态库；应用须使用同一源码版本的头文件和库并重新编译。不承诺跨版本二进制 ABI，也不把配置结构大小或 opaque/private words 布局当作持久化格式。
- 初始化配置时使用对应 `*_config_init()`；升级时检查源级 API 与线协议变更。线协议版本/帧字段的校验不等于任意新旧应用混部兼容性已获证明。
- 检查所有返回状态，包括容量拒绝、超时、关闭和可重试销毁。失败回收仍持有 publication 时，必须保留对象并按接口契约重试，不能忽略错误后释放用户回调存储。
- stop/drain 不抢占用户回调，业务期限不是所有锁竞争、排队、回调和销毁屏障的硬实时返回保证。Connector attempt 期限当前从初始非阻塞 connect 调用返回后开始；不要把它当作整个 API 排队时长的 SLA。
- 有限 generation 只在未回绕窗口内隔离旧句柄；aux 使用非零 32 位代次，不能宣称永久无 ABA。

## 上线前必须确认

1. 安全边界：CRC 是损坏检测，不能提供身份认证、机密性或对抗主动篡改。库没有集成 TLS；不应直接暴露到不可信公网。应用必须提供实际验证的认证/授权及传输保护方案。
2. 容量与运维：基于目标硬件、载荷和连接数实测延迟分位、拒绝率、CPU/RSS、fd上限及资源饱和后的恢复。不要把关闭负载或增大资源后取得的吞吐当作原配置保证。
3. 故障与长稳：跨进程 TCP、断网/半开、慢读写、重连风暴、长时间运行和升级/回滚须在目标环境验证；普通 CI 与有限故障注入不证明所有故障组合。
4. 业务语义：RPC 成功不等于数据持久化，也不提供业务幂等或自动安全重放。重试前由上层确定请求是否可能已经生效。
5. 许可：仓库尚未明确项目级 LICENSE，不能从格式配置的许可证推断自有 SDK 的许可。正式分发前需维护者明确选择并落实 LICENSE/SPDX/第三方来源；本说明不代替许可授权。

因此，“既定平台上的 CI 与回归通过”只能作为受控部署候选的工程证据，不能替代
上述安全、容量、故障和许可验收，也不意味着 #154 的全部工程整改已经完成。

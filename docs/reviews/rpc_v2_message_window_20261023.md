## 缺陷与实际复现

普通 V2 已有本地方法/窗口配置检查，Client 还有对端初始窗口检查；原问题并非
“所有默认调用死锁”。共享 Channel 的响应和直接流发送没有永久大小拒绝，
直接 Channel 使用的信用批量阈值也缺少整消息准入的活性限制。

| 回归 | 修复前实际观测 | 修复后 |
|---|---|---|
| 对端 W=128，记录 L=129，未持有在途消息 | `send=1`，即 AGAIN；反复等待无新增信用来源 | BAD_LENGTH；缓冲、消息序号、状态和已发字节不变 |
| W=128、M=256、阈值128，OPEN 已消费48字节 | advertised 仍128，应为176；下一条128字节记录不能准入 | 消费信用及时更新，连续最大合法记录完成 |
| 普通服务端 640字节正文，对端内部窗口560、协商消息能力1072 | 在加入传输大小拒绝后，原错误适配返回 UNAVAILABLE=14 | 同步/producer 均 INVALID_ARGUMENT，唯一终局和全部回收 |

第三个 RED 验证错误分类，运行于传输拒绝已加入、RPC 分类尚未修改的中间版本，
不冒充完整旧版的服务端超时复现。原始失败全部保留。

新增测试首次编译时错误地把返回 void 的 producer_release 当作状态值使用；
修正该测试后才执行第三个 RED。这是测试编写错误，没有记为产品缺陷。

## 实现与不变量

- 每个流槽记录对端初始窗口：远端 STREAM_OPEN 或本地 OPEN 的第一次
  WINDOW_UPDATE。后续累计信用不改变单条消息上限；槽位初始化/释放会清空它。
- 已准入流发送满足 L <= min(W,M) 才进入当前信用/发送队列检查；超限立即
  BAD_LENGTH，不接管缓冲、不递增字节和消息编号。暂时占用的窗口仍是 AGAIN。
- 接收端把期望阈值限制到 T <= W-min(W,M)+1。未通告消费债务 d<T 时，
  完全释放后仍有 W-d >= min(W,M)，足以发送下一条合法消息；否则发信用更新。
  比较 T-1 后再加一避免 uint64 回绕。已停止信用、控制池压力重试均保留。
- 同步批次和异步 producer 的 BAD_LENGTH 映射 INVALID_ARGUMENT，停止重试
  并使用既有终局/RESET 和存储释放流程；已选终局不被覆盖。

所有字段继续由 Channel 锁保护，没有新增队列、任务、线程或按消息分配。
窗口是网络字节信用；普通 V2 复制入有界工作事件后可归还网络信用，事件存储
仍保留自己的内存预算。该修复没有把网络信用释放当作所有副本的释放证明。

## 覆盖与本地结果

| 验证 | 结果和证明范围 |
|---|---|
| GCC release 全量 | 80/80，55.078秒，包含原窗口控制重试/RESET/排空/取消/构造清理 |
| 聚焦三目标 | rpc_record_stream、rpc_v2_server、channel_control_retry，3/3 |
| GCC ASan/UBSan | 同三目标 3/3；detect_leaks=1、halt_on_error=1，无运行时诊断 |
| 双向不对称窗口 | 请求 W=128、响应 W=64；L=W-1/W/W+1，累计已发超过 W 后再次拒绝 W+1 |
| 分片与状态 | 256字节和32字节帧；既有逐字节 Record 输入；拒绝不改调用状态和所有权 |
| 已持有窗口 | 第一流保留96/128信用，另一流完成零消息 MANY 调用；释放后第一流恢复并成功 |
| 普通门面 | 两端各自配置合法但方法/窗口不对称；无 deadline 的同步和 producer 大响应均结束；旧调用成功，started=finished=3，inflight=0 |
| 回收 | producer CLOSED 后拒绝提交，独立引用显式释放；Client 排空、双端销毁及内部绑定预算归零 |

## 成本与性能边界

x86_64 GCC 的 sizeof：流槽 **160→168字节**；Channel=1032、Connection=776、
Reactor=2584 均不变。每槽增加8字节，固定比较和阈值计算是 O(1)。
旧配置阈值若阻碍活性，调整后会增加信用更新；安全批量阈值继续保留。

真实三组实验均发送 OPEN 和三条最大合法 MESSAGE，统计包含初始流准入更新：

| W / M / 配置阈值 | OPEN 后绝对信用 | WINDOW_UPDATE 次数 |
|---|---:|---:|
| 128 / 256 / 128 | 176 | 5 |
| 256 / 128 / 200 | 256 | 3 |
| 256 / 128 / 32 | 304 | 5 |

第二组证明没有一律把阈值设为1。普通 V2 原来已经限制阈值，本次没有增大默认
窗口或池容量。没有新增吞吐/尾延迟压测，不能从这些功能结果推导40k达标；
原 [PERF-V2-03](rpc_v2_stream_refusal_20261023.md) 的性能负结果仍有效。

## 主会话审查

按 code-review-checklist 检查设计、逐行正确性、跨文件合同和范围：

- 大小检查发生在所有权转移与计数提交前，采用 uint64 总和；状态/连接检查仍先行。
- 初始窗口在两种开流方向各写入一次，累计更新不覆盖，槽复用不会继承旧值。
- 阈值非零来自原配置归一化；减法取 min，T-1 和条件内加一有明确算术边界。
- 没有新分配/引用/回调重入，原关闭、取消、已选终局与弱句柄边界保持成立。
- 同步和 producer 两条适配路径使用相同错误分类；公开说明不承诺复制成功即发送成功。
- 回归覆盖真实流控而非把 AGAIN 注入当作窗口行为，RED 原因与测试编写失败分别记录。

现有 GCC/Clang 告警保持 unverified。本次只映射 Channel 中未修改语句的位置：
GCC 699→700，Clang 3511→3524；字段/列/检查器/消息不变。映射证据在 JSON。
新的实际分析仍须由候选 CI 验证原有1/9观察集，没有将位置调整当作安全裁定。
未发现本切片的待修阻断项；这是主会话审查，不是独立审核。

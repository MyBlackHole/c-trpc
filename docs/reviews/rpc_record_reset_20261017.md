# V2 单流重置、调用取消与安全退役

## 本阶段范围

本阶段接续 [Server 截止时间](server_record_deadline_20261017.md)，基于
[PR #272](https://github.com/MyBlackHole/c-trpc/pull/272) 的
`01bb608183b4899a10a711a4b37fc50efb7aa489`。它让 V2 Client 的取消和本地超时
通过真实连接把停止原因传到远端并合作取消，使 Server 能在业务尚未退出时先终止网络。
目标流的协议结果、工作任务的静默和传输槽退役分别由原有所有者负责。

历史记录中“没有调用级 RESET”和“取消后继续补信用排空晚响应”的描述是此前
版本的边界，本阶段以这里的新合同取代；旧验证记录保留原文。公开 SDK、默认
Echo 和现有基准仍走 V1，不能据本阶段测试宣称整个 RPC 迁移或 V2 性能验收完成。

## 协议和能力协商

RESET 是 Channel 控制帧，不是第二套 RPC 记录解析器。RPC Record V2 与 Channel
握手的协议版本是不同层次；本阶段仍使用既有 Channel 版本并协商独立能力位。

| 字段 | 合同 |
|---|---|
| `type` | `TR_FRAME_STREAM_RESET = 14` |
| `flags`、载荷长度 | 均为零 |
| `stream_id` | 当前物理连接上已有流的非零 ID |
| `message_id` | 取负号后的有限 `tr_status` 原因编码 |
| 能力 | `TR_CHANNEL_FEATURE_STREAM_RESET` |
| 上层事件 | `TR_STREAM_EVENT_RESET`，携带传输原因 |

V2 两端同时设置 `feature_bits` 和 `required_feature_bits`。本地必需能力必须
属于本地声明集合；HELLO 和 HELLO_ACK 都在发布 UP 之前检查对端是否接受全部
必需能力。缺少 RESET 的对端不能先握手成功、再让后续取消永久返回不支持。
普通 Channel 可以继续把能力声明为可选。

| 传输原因 | RPC 接收侧终局 |
|---|---|
| `TR_ERR_CLOSED` | `CANCELLED` |
| `TR_ERR_TIMEOUT` | `DEADLINE_EXCEEDED` |
| `TR_ERR_NOMEM` | `RESOURCE_EXHAUSTED` |
| `TR_ERR_STATE` | `INVALID_ARGUMENT` |
| `TR_ERR_SYS` | `INTERNAL` |

映射集中在 RPC 私有适配头。Channel 和 Reactor 不解释 RPC 状态。RESET 只表达
停止原因；错误 FINAL 未被接受时，不能保证完整业务状态送达。已经由记录状态机
接纳的合法 FINAL 保留原结果，后来的 RESET、连接错误或本地取消不覆盖它。

## 双向停止与发送责任

每个方向、每条流至多发送一次 RESET。收到首次 RESET 的一端停止新业务收发和
接收信用，通知上层并发送本方向 RESET。双方各一次既是停止请求，也是对端发送
静默的确认，不再引入额外 ACK 帧或回声循环。双方主动取消可能使用不同原因；
本地首个原因和对端方向的原因独立保存，同一对端方向的重复原因必须一致。

`tr_stream_reset_on_owner()` 只在所属 Reactor 所有者中调用。返回 `TR_OK` 表示
Channel 已接管发送、重试和确认责任；它不表示帧已经写完、对端业务已退出或
网络槽已经释放。接管前失败必须保持原状态，由调用者保留重试责任。

传输 OPEN 尚未收到初始 WINDOW_UPDATE 时，主动 RESET 返回 `TR_AGAIN`，等待
对端明确准入。这个传输 OPEN 与 RPC 的完整 OPEN 记录不同：传输已经准入而
RPC OPEN 尚未收齐时可以 RESET。Client 收到尚未准入的提前 CLOSE 拒绝时，以
普通 CLOSE 确认，不能向没有准入槽的对端新建 RESET 责任。

每个连接在原 GOAWAY 预留项之外独立内嵌一个 RESET 发送项，不占普通 DATA 或
控制发送池，也不消耗命令环的新容量。登记时固定既有命令的序列前沿；重试不
移动此前沿，RESET 与 GOAWAY 同时等待时保持接受顺序。RESET 沿原 FIFO 排在
已接受 DATA 和信用之后，不使用优先绕过白名单。已开始写入的帧必须完整写完，
不丢弃旧发送项的载荷，也不把截断数据伪装成新帧头。

命令逐条到达固定前沿时即插入预留项，不能等到整批命令处理结束。否则
后接受的 SEND 会在同批中先进入 FIFO，例如 CLOSED 回调立刻复用网络槽发出
新 OPEN，就可能越过该槽旧代次的 RESET 确认。重复登记 GOAWAY 时也要根据仍
在等待的 RESET 重新固定相对先后，不能沿用上一个已发送 GOAWAY 的次序。

Channel 复用原维护定时器和有界轮转游标推进多个 RESET。定时器的重试责任先
建立成功，随后才能发布流状态改变。普通发送池耗尽、命令环满或短写不会让
已经接管的停止责任消失。

本方向普通 CLOSE 一旦被接受，不再主动追加 RESET；如果随后收到对端 RESET，
仍要对称响应。这保护 Server FINAL+CLOSE 与 Client 尚未收包时取消的交叉：
Server 保留先前 OK，Client 保留自己的 CANCELLED，在途响应不再交付 Client。

## 分层退役屏障

| 对象 | 可退役条件 | 必须继续持有的内容 |
|---|---|---|
| Client 调用绑定 | 已选择并报告终局，Channel 已接管 RESET 或普通关闭 | RESET 未接管时的槽、绑定和重试责任 |
| Server 路由与分发调用 | 原任务真实退出并交付完成，唯一终局回调已发生 | 运行中的任务、输入 view、拥有型回复及业务参数 |
| Channel 网络流 | 本方向 RESET 已被 Reactor 接受，已收到对端 RESET，停止事件已通知 | 冻结信用、迟到分片的有限状态和确认责任 |
| Reactor 发送项 | 真实写完，或连接停止路径释放 | 已接受帧及其拥有的载荷引用 |

分发器新增只读 `tr_rpc_record_dispatch_result_on_owner()`，供 Endpoint 观察
已经选定的终局。这个快照不能证明工作线程静默。Endpoint 可以据它先发送 RESET，
但仍必须等待原 dispatch terminal 回调后才报告和释放业务对象；不合作线程不能
被强制抢占或提前释放。

RESET 的双向网络确认可以早于 Server 工作任务退出。同一个传输槽的新代次因此
可以使用另一个空闲路由；准入的重复检测必须同时比较槽号和代次。旧任务的路由
仍按原弱句柄保存，不能被新流覆盖。业务容量确实耗尽时仍要拒绝，网络槽释放不
会虚构可用的工作容量。当前占用统计只计算活跃调用，退役槽残留的终局字段不再
计入 `terminal_calls`。

## 迟到帧与错误作用域

进入 RESETTING 后立即释放未完成重组，不再给该流补信用、交业务或通知可写。
对端 RESET 之前的在途 DATA 仍按精确流身份、物理连接、帧形状和已公布的累计
信用校验，只丢弃字节。原消息语义仍可信时继续检查序号、FIRST/LAST 及消息大小；
因已知消息语义损坏发起重置时，以一个有限失步标志停止重复应用已经不成立的
逻辑消息规则，仍坚持帧边界、归属和冻结字节额度，不重新分配重组存储。

在途 WINDOW_UPDATE 仍校验原约束，不重新开放业务。RESET 之前到达的普通 CLOSE
只记录半关闭，不能越过 RESET 确认门禁释放流。收到对端 RESET 后，同方向再来
DATA、WINDOW_UPDATE 或 CLOSE 属于协议错误，因为 RESET 已是该方向的 FIFO
静默边界。

| 错误位置 | 处理范围 |
|---|---|
| 已归属调用的 RPC 记录、方法、配额或业务错误 | 选择该调用终局；可发送详细错误 FINAL，否则通过 RESET 收尾 |
| 本方向尚未 CLOSE、合法信用内的流重组资源不足 | 该流 `RESET / NOMEM`，其他流继续 |
| 同上、线帧边界可信的消息序号、分片逻辑或消息大小错误 | 该流 `RESET / STATE`，有界丢弃已知失步消息 |
| CRC、无法恢复的线帧形状、无法归属的 DATA/信用/RESET、错误物理连接、超出已公布信用 | 连接级失败 |
| 对端 RESET 之后的 DATA、信用或 CLOSE；原因不一致的重复 RESET | 连接级失败 |
| 本方向普通 CLOSE 已接受后再遭遇消息错误或重组资源不足 | 连接级失败；不建立没有双向 RESET 的第二条收尾路径 |
| 入站 transport OPEN 无可用槽，或初始信用无法被发送层接受 | 明确连接失败；不能静默遗留对端 OPENING |

流退役后使用大小固定为 `max_streams` 的精确记录环，只接纳保留窗口内、同一
连接代次与流 ID、同一对端原因的重复 RESET。它不放宽未知 DATA、信用或任意
RESET。记录淘汰后的老重复不再合法；合法 TCP 对端本来每方向只发一次。

本地流 ID、流槽代次及物理连接槽代次耗尽后明确拒绝，不回绕；连接的辅助事件
与定时器代次不在本次修改范围。对端 OPEN 的 ID 前沿属于实际
物理连接：共享连接的两条逻辑 lane 共用前沿，独立连接分别维护，不能用跨 TCP
到达顺序判断重放。

## 验证方法和当前边界

新增低层测试使用真实 socket 和 Reactor，以原始对端精确控制 RESET、晚帧、
短写和 EAGAIN。新增 `test_rpc_record_cancel` 使用真实 V2 Client、Server、TCP
和任务执行器，覆盖 HALF_CLOSE 后远端取消、FINAL 接受前取消、FINAL+CLOSE
接受后的跨端终局交叉，以及 Client 本地期限经 RESET 到达无限期限的 Server。
CAP=2 场景要求并行流持续工作、原业务未退出时保留其输入、退出后强制复用唯一
空闲槽、两端旧句柄失效和预算回到连接空闲基线。

原 Client 多窗口场景继续要求不合作业务产生 12,435 字节迟到回复，超过 8,192
字节窗口；本阶段验证这些尚未接受的回复被取消丢弃。在途已接受 DATA/FINAL 的
责任由新的交叉测试单独覆盖。Server deadline 专测的运行中任务允许 Client
先收到 RESET 终局，仍严格要求 Server 在真实业务门闩退出后才报告。

所有故障包装器仅在测试目标链接，不向生产加入测试开关。新增接口是实际宿主
需要的只读所有者查询，测试没有依据私有结构布局直接伪造任务状态。

不合作对端永不确认时，固定数量的 RESETTING 网络槽可保留到断连或销毁；不
合作业务永不退出时，相关任务对象必须继续持有。本阶段没有引入强杀线程、后台
无界排空、慢 OPEN 准入期限、GOAWAY 最后受理边界、TLS 或完整异步 producer API。
本次模块收紧限于 RPC 原因翻译、只读结果查询和 Channel/Reactor 发送责任，
不是全库模块重构完成声明。

### 首轮静态诊断及处理

同一冻结版本的 Clang 14 与 GCC 11 静态分析均实际完成全部 42 个生产单元，
没有分析失败的源文件。Clang 分析耗时 88.267 秒，分析退出 0，但精确告警门禁
退出 1；GCC 分析与门禁耗时 34.376 秒，实际退出 2。首次失败原样保留，不能
用功能矩阵全绿代替静态门禁。

其中三条是已有诊断随源码增加而移动的位置：

| 分析器 | 位置 | 原行 → 新行 | 身份核对 |
|---|---|---:|---|
| Clang 14 | `reactor.c` 的 `items` 潜在泄漏 | 307 → 314 | 分配函数全文相同，原检查项、列号和消息相同 |
| Clang 14 | `channel.c` 的 `build.channel` 潜在泄漏 | 2607 → 2999 | 原分配与自动清理绑定相同，实际路径在原角色校验分支返回 |
| GCC 11 | `channel.c` 的 `owned` 潜在泄漏 | 582 → 609 | 协议缓冲分配函数全文相同，原检查项、列号和消息相同 |

行号调整前已核对完整生产单元、源文件、列号、检查项和诊断文字。Channel 的
构造函数确实包含本阶段新逻辑，但该 Clang 路径在原角色检查处结束，尚未执行
新能力条件；自动清理函数全文也与基准相同。记录只调整这三处位置，仍保留
原来的 11 条 Clang、2 条 GCC 告警及 `review_state: unverified`。

Clang 另新增一条 `UndefinedBinaryOperatorResult`，声称
`((uint64_t)generation << 32)` 将 1 左移 32 位无法由 `uint64_t` 表示。
没有把它加入记录或关闭检查。独立使用原 Xmake 数据库再次分析真实 Reactor
单元，3.106 秒后精确复现；从同一编译命令取得的宏和 AST 确认目标是 `-m64`、
`-std=c11`，`uint64_t` 为 64 位无符号 `unsigned long`，位移左操作数和结果
都是该类型。

独立最小诊断保留了原子的 64 位槽读取、提取高 32 位、检查代次并加一、再转为
64 位组合令牌的完整链路，同时用编译期断言检查整数宽度。当前写法和两种
32 位递增改写均产生同一告警；仅将加法明确放在 64 位域内的两种写法不再
告警。该探针只是诊断证据，不计入正式生产数据库或 42 单元覆盖。

原移位本身有定义：任意 32 位无符号值扩大到 64 位后左移 32 位，最大结果为
`0xffffffff00000000`，低 32 位状态与其不重叠。本阶段原上界还保证
`generation + 1 <= 0xfffeffff`，因此原递增也不会溢出。修订只明确其计算宽度：

```c
if (generation >= TR_REACTOR_CONNECTION_GENERATION_MAX)
        return 0U;
return (uint32_t)((uint64_t)generation + UINT64_C(1));
```

上界保证最后的窄化不丢位，与此前函数对全部 `uint32_t` 输入等价。这解决固定
Clang 14 的位宽建模问题，不宣称原程序存在实际移位 UB。令牌编码、代次耗尽
行为、分析器版本、检查集合及生产编译选项均未改动。

## 实现边界

Channel 3 新增 STREAM_REFUSED，仅拒绝还没有初始信用的 OPEN。流槽满不再连带中止连接；普通 V2 将该终局映射为 RESOURCE_EXHAUSTED。开流端先使精确句柄失效，再回调，既有取消/截止结果不被覆盖。接收端没有为被拒绝流分配槽位或交付业务，不等待回包，不增加拒绝墓碑。

每条物理连接最多保存一个待拒绝 ID；与 RESET 共用现有内嵌终止预留，保留命令前沿、DATA FIFO 与 GOAWAY 顺序。预留忙时暂停 RX，既有维护定时器重试；等待的条件是发送项释放，不是流槽或对端回包。拒绝与 RESET 都等待时按上次获准类型轮换，RESET 内部仍使用原有流游标。

本机 x86_64：Channel 1016 → 1032 字节；Connection 776、Reactor 2584 字节不变。预算继续按实际 sizeof 计算。无动态拒绝表；过载时需要有界扫描当前流槽。新拒绝重试仍可能等待 25ms，不能据此声称已经达到 40k。

Channel 只接受握手版本 3，必须同时升级两端。线帧信封仍为 1，RPC Record 仍为 2；不新增稳定公开 API 或改变默认容量。

## 测试证据

- 槽满 RED：原实现在等待拒绝帧时读到 EOF；修复后连续拒绝超过槽总数的新流，已有流仍交付，归还槽位后继续准入。
- RPC RED：只有传输拒绝、尚未接入 RPC 终局事件时等待超时；接入后 3 次 RESOURCE_EXHAUSTED、1 次先发生的 CANCELLED 和 1 次正常完成均只回调一次。服务端只受理原有调用，客户端 started=finished=5、inflight=0。
- 公平性 RED：阻止拒绝帧完成部分写后，连续 OPEN 抢在等待的 RESET 前面。轮换修复后 RESET 与拒绝按约定顺序前进。
- 传输回归覆盖真实普通控制池/命令队列满、共享预留幂等和类型区分、部分写、维护定时器失败、停止/解绑、排空接管、拆分连接进展、槽代次复用、未知/重复/已受理/错连接拒绝以及严格线帧形状。
- GCC release 全量 80/80。测试新增的命令队列场景最初把已占用的 4 条 PING 命令漏算，导致测试断言失败；修正填充数量后全量通过，原失败日志保留。
- GCC ASan/UBSan（含泄漏检查）Channel 排空、普通 V2 Server、RESET/拒绝 3/3；随后补充的拆分连接进展场景在同一 ASan/UBSan 目标通过。
- 所有临时文件、构建和日志使用工作区 `build/test-tmp` 与 `build/perf-v2-03`。
- 候选 `ca19366` 的 push CI `39909830068` 中 GCC 11 与 Clang 14 各分析 43 个生产单元，分别仍为 1/9 条既有诊断。失败仅为 Channel 位置移动：GCC 695→699、Clang 3373→3511；两份完整 Channel 诊断去掉行号后与前次工件逐字相同，原源语句相同。核对后更新精确清单，在工件副本重放为零新增/零缺失，`review_state=unverified` 保留。原失败报告和全部分析日志随证据归档。

## 主会话审查

按 code-review-checklist 检查架构、逐行修改、跨模块事件传播及范围。没有子 agent 或独立审查声明。

- 输入和整数：固定原因、空载荷/标志、非零流 ID；仅精确本地 OPENING 可接收。未知或重复拒绝不被静默吞掉。
- 并发和回调：Channel 状态由既有锁保护；发送预留仅在 owner 调用；解锁并退役槽位后通知上层；取消先到仍保留原终局。
- 生命周期：断连清除精确连接待办，排空接管未提交拒绝；已提交帧继续按 FIFO 排空；解绑恢复借用连接 RX；停止释放内嵌项。
- 内存和性能：固定状态增加 16 字节/Channel，无逐拒绝分配；过载扫描有界，终止预留不受普通池/命令容量限制；吞吐和尾延迟需以相同配置实验判断。
- 范围：没有扩大默认容量，没有引入重连/重试或隐藏失败样本；#239 的完整 V2 目标仍未完成。

## 同配置性能与资源账本

AMD Ryzen 7 PRO 4750U、Linux 7.2.11、GCC release、TCP IPv4 loopback；前后均为三档各三次，每次 offered=10,000、计划 40,000/s、16 个发生器、每个 window/capacity=64、warmup 合计 32、deadline=3 秒。脚本容量 32/128/256 对应每连接 max_streams=max_calls=64/256/512，消息和初始信用配置未变。独立运行，未与本地编译或测试并行。

基线 default 另有 54 次 submit_again；修复后所有档位该值均为零。两侧所有样本 deadline 和 invalid_response 都为零。18 个到达/提交/终局账本均收敛，服务端 started=finished、队列/运行任务归零，16 个 peer 全部回收，drain 成功。修复后每个样本的服务端受理数恰好为成功调用数加 32 次 warmup，证明未受理拒绝没有进入服务端 RPC 计数。

小档连接失败被 47 次独立资源拒绝替代，成功数量增加；发生器丢弃也增多。成功延迟指标（每次 16 个发生器成功 P99 的最大值，再取三次中位数，**不是全局 P99**）：small 231.72 → 362.70ms，default 261.75 → 228.75ms，large 279.26 → 291.60ms。小档与大档该指标变差，不能把错误隔离修复描述成所有档位的性能优化。

服务端 CPU 中位数 small/default/large 为 0.418→0.613 / 0.598→0.617 / 0.645→0.675 秒，发生器 CPU 合计为 1.099→1.332 / 1.291→1.334 / 1.230→1.292 秒。服务端峰值 RSS 各档均为 27,252→27,308 KiB，发生器峰值之和均为 436,032→436,928 KiB。这些是含启动/warmup/drain 的进程生命周期测量，不能当作每调用 CPU 或协议预算。

所有档仍为 clean 0/3：控制池压力、发生器延迟/丢弃均存在，若干样本还有 DATA TX 池压力。三次测量不能精确拆分调度和环境波动。后续需要继续分析 25ms 终止预留重试、消费信用与负载生成质量；本切片未达到 40k，也未完成整体 V2。

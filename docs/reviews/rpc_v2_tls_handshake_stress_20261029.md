# 长寿命 Server 的 TLS 持续握手压力诊断

日期：2026-10-29；关联 #234、#241、#247。版本仍为 `2.0.0-dev.178`。
源码固定为 `60630875a2e1fe0c36d66e5d459b8e8040c0f69e`，该提交关联的远端检查
13/13 成功：[CI](https://github.com/MyBlackHole/c-trpc/actions/runs/40865591738)、
[RPC smoke](https://github.com/MyBlackHole/c-trpc/actions/runs/40865591771)。
本次只归档独立诊断驱动、结果和说明，不改变运行时/API/ABI/wire 或 CI 标识。

## 场景与实际验证

既有 16 个慢握手加 48 个超额连接回归验证单次有界突发；独立分配账本的
34 轮 mTLS 周转验证 session/profile 释放。本次补充同一普通公开 Server 在
持续混合连接压力下的进展和进程资源观测，不重复宣称前两者的资源覆盖范围。

通过现有 Xmake 入口构建 trcore/bench_rpc，复制冻结二进制；使用 GCC Release、
Linux 7.2.11 x86_64、OpenSSL 3.6.5、Python 标准库。共享开发机未设亲和性隔离，
不是 TEST-E 固定基准机。二进制 SHA-256 为
`7cd245121138a344bd80d9d19a9f47137d8ebf9c6c1ca0761c9a9c3dc39a117a`。
源码、二进制、实际脚本、原始数据摘要及参数见[汇总数据](data/tls_handshake_stress_20261029_summary.json)，
全部 617 个进程资源采样见 [CSV](data/tls_handshake_stress_20261029_resources.csv)。

- Server 保持既有 32-peer、128-call 配置和 10000ms 握手期限，不为通过压力增加
  窗口、线程或队列。测试没有修改服务端私有计费、钩子或协议。
- 先建立一条健康 TLS 1.3 连接，以 100 RPS、4 KiB 正文、双向 Zstd 运行 600 秒。
  32 次预热不进入测量请求数。TLS 为服务端认证，未配置 mTLS。
- 另一驱动以每秒 64 次目标速率循环静默、部分 TLS 记录逐秒滴灌、发送合法
  ClientHello 后本地中止、明文输入四类；并发 socket 上限为 64。
- 结束后关闭压力连接，空闲观测 12 秒，再新建健康 Client 完成 64 次恢复调用。
  最终 Server drain 与 destroy 均成功；所有测试产物只写工作区 build/。

先完成 30 秒预检，再完成 600 秒观测；修正下述元数据标签后又完成一次独立的
30 秒复核。两个 30 秒场景各有 3000/3000 正常 RPC、64/64 恢复；均非容量测量。
[归档驱动与复现](experiments/tls_handshake_stress_20261029/README.md)说明证书、构建、
输出位置、固定源和错误标签的恢复方式。

## 调用与连接账本

600 秒测量中 offered/attempted/accepted/completed/ok 全部为 60000；发生器丢弃、
提交拒绝、deadline、RPC 错误和正文错误均为零。Server 含预热与恢复共
60096/60096，结束时任务排队/运行均为零；UNAVAILABLE/RESOURCE_EXHAUSTED 与
RX/TX/CONTROL TX 池耗尽事件均为零。压力期间使用的是先建立的健康连接，
不能据此声称 peer 满载时新连接也能被准入。

| 压力类型 | TCP 尝试/连接完成 | 脚本发现远端关闭 | 脚本主动关闭 |
|---|---:|---:|---:|
| 静默 | 9600 / 9600 | 9589 | 11 |
| 部分记录持续滴灌 | 9600 / 9600 | 9580 | 20 |
| ClientHello 后中止 | 9600 / 9600 | 4994 | 4606 |
| 明文输入 | 9600 / 9600 | 9600 | 0 |

合计 38400 次 TCP 连接，连接错误及发生器跳过均为零；每类 attempted 与三种
退出分类完整相等。TCP 连接完成不等于进入 TLS session：大量连接可能被 peer
容量直接拒绝。Server 只报告 2 个 ready peer（正常与恢复 Client）和 6689 个
reaped peer；不能把 38400 全计为已准入 TLS 握手或用此相减推导精确拒绝数量。

静默和滴灌分别有 725/1087 条在客户端观测寿命至少 5 秒后远端关闭，最长分别
10.004539/10.003348 秒。滴灌未使这些慢连接无限续期；寿命从 connect 发起算起，
含脚本调度与 TCP 时间，不是逐条 Server accept/deadline 的精确测量。

本场景成功 RPC p50/p99 为 30.303490/36.185598ms；提交迟到 p99 为 146.467us、
最大 4579.954us，测量窗口外排空尾部 24.929316ms。Server 生命周期 CPU 为
381.657915 秒。这些只是此负载/主机的观测，没有无压力同二进制对照或容量目标，
不据此宣布吞吐、尾延迟或每握手 CPU 成本达标。
Reactor 记录 34969657 轮，其中 epoll_waits=34906467、epoll_polls=63190；前者
按请求的非零等待超时分类，不证明实际睡眠。该频率与 CPU 成本仍需同二进制
隔离必要工作和可能空转，不能因全部调用成功就认定调度成本合理。

## 进程资源及限制

| 观测项 | 617 次采样范围 | 压力解除后、恢复调用后 |
|---|---:|---:|
| Server RSS（KiB） | 12044–24280 | 19412 |
| Server PSS（KiB） | 5093–17288 | 14717 |
| 匿名 RSS（KiB） | 2656–14752 | 12940 |
| fd 数 | 8–40 | 8 |
| 线程数 | 7–7 | 7 |

RSS 在初期升高后未呈现随累计连接数持续增长的趋势，压力解除后也未回到初始值。
没有 allocator live、线程局部缓存或堆调用栈证据，不能将残留直接归因为泄漏、
缓存或其他特定所有者，也不能用 RSS 回落证明对象都已释放。
进程退出记录的 getrusage 峰值为 **29096 KiB**，高于定时采样最高值；采样范围
不是连续资源上限。/proc 的 status/smaps_rollup 与退出统计分开保留，不拼成
同一时刻的精确账本。没有采集逐 socket 的内核实际驻留。

## 元数据错误与更正

观测版驱动遗漏 metadata() 的 tls/compression 参数，原始顶层误写为 false/none；
实际命令、Server ready 和 Client open_phase 三处均确认为 TLS/Zstd。原始文件
没有重写，另存 metadata_correction.json；汇总明确保留更正依据和原始文件摘要。
归档脚本只修这处标签调用，修正后的 30 秒复核已验证标签与运行结果一致。
没有借用错误标签的运行结果充当明文基线，也没有将后续复核冒充 600 秒源版本。

原始证据在忽略目录 build/performance-20261029/tls-handshake-stress-600s/，
预检与复核分别在 tls-handshake-smoke-30s/、tls-handshake-metadata-smoke-30s/。
源码/脚本两版本的摘要关系在归档说明中可还原；证书和私钥没有提交。

## 发布边界

本次增加普通 Server 持续未完成/中止/非法握手期间的健康连接进展与恢复证据。
它不替代 OpenSSL 全部活跃分配、最坏证书/握手消息、mTLS/凭证轮换、压缩取消
迟到结果、内核驻留、分域及全局硬预算、目标平台和固定基准机容量验收。
#234/TLS-E、#241、#247、CTM1 类型契约和完整发布目标继续开放。

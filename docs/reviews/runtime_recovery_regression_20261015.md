# MSG-D1：多分片独立回收与异常退出组合回归

## 基线与范围

基于 #256 的 `511e691407826939fcfabe19a12532462909f584`，树为
`c23f5105741ba6629e2d17da8cae5040f7d7f1dd`。落实 #256 审查评论
`6195399134` 提出的三个有限场景，关联 #239、#241、#243、#247、#248。

本轮不重新实现 #256 已有的恢复租约、Runtime 服务所有权或停止域回调；
不机械叠加 #257 的近义所有者接口，也不复活已关闭的重复方案 #258。
新增覆盖使用真实 Runtime、Reactor、执行器和 Zstandard，不使用事件循环替身。

## 实际复现的问题及修复

原 `tr_runtime_destroy()` 在 `tr_runtime_stop()` 成功后按顺序释放分片，
遇到第一个非成功结果就返回。两分片都已停止、分片 0 有应用保留的消息输出时，
分片 0 返回 `TR_AGAIN`，分片 1 的 Reactor 等已静默资源却完全没有释放。
这不是已确认的悬空引用或数据竞争，而是独立资源域被其他分片的保留状态阻塞。

新多分片测试在未修复实现上稳定触发断言：

```text
tr_runtime_shard_reactor(f[i].shard) == NULL
```

修复仅改变已经全局停止之后的存储释放遍历：尝试所有分片，汇总结果，
硬错误优先于暂时的 `TR_AGAIN`，同类硬错误保留先出现者。只要任一分片
未完成，Runtime 与整个分片数组继续存活；只有全部成功才释放预算外壳。
停止尚未完成时仍直接返回原停止结果，不扩大到未静默的分片并发拆除。

原有分片释放步骤和重试状态保持不变。后续分片不读取其他分片私有存储，
因此无需等待另一个分片的应用输出归还后才释放自身 Reactor。
部分释放后的重启继续由已有检查明确拒绝，不允许在缺失父资源上重新启动。

## 三组组合场景

### 1. 真实部分销毁后原所有者退出

先在原 owner 中进入真实执行器销毁，实际执行 `pthread_cond_destroy()`，
随后仅在该执行器销毁调用内令 `pthread_mutex_destroy()` 返回 EBUSY。
保留 fd 和对象，随后在真实 `epoll_wait()` 中注入 EIO，使原 owner 退出。

恢复必须先取得父线程已 join 的租约，采用已有 `adopt_cleanup`，只能继续
尚未完成的 mutex 销毁，不能对已销毁条件变量 signal、broadcast、wait 或再次 destroy。
恢复期间再注入一次 mutex 销毁失败，验证租约、fd 和销毁进度继续保留，
父 Reactor 的 start/destroy 被拒绝，最后一次重试恰好关闭 fd 并释放对象。

该场景在 #256 基线已经通过，**本轮没有将它误记为修复过的缺陷**。
测试包装通过真实销毁的调用范围识别同步对象，不读取执行器私有结构。
检测死条件变量的断言在调用 pthread 之前执行，避免负向试验真的触发未定义行为。

为验证覆盖有效性，仅在本地构建一个故意删除 `executor_retiring` 保护的
错误变体，不修改最终源树。该变体会在恢复时重新 stop/broadcast，测试准确失败：

```text
condition != atomic_load(&destroyed_condition)
```

它是测试有效性的反向证据，不能当成基线本身存在该错误的证据。

### 2. 两分片输出、切片及错误优先级

两个启用消息服务的真实分片各保留一个正常输出及一个单字节切片。
停止全部分片后，在首个或第二个分片分别注入一次 Reactor destroy 失败；
仍应尝试释放另一分片，并返回 `TR_ERR_SYS`，不能被另一分片的 AGAIN 掩盖。
重试后两个 Reactor 都应释放，但各自包含预算的 Runtime 分片外壳继续有效。

分别在不同线程、按两种相反顺序释放原始输出和切片。原始输出释放后，
剩余切片继续持有整份存储的容量；最后切片释放时只归还对应分片的预算。
另一个分片的计费不变，所有切片内容保持有效，部分销毁后的 start 明确拒绝。
最终两个预算域均归零后才允许整个 Runtime 销毁。

### 3. 同一服务中混合存在不同结果状态

同一 Runtime 内固定以下状态，再令父 owner 发生真实 EIO：

- 已正常交付并被应用持有的成功输出；
- 后端已完成，但 owner 尚未交付的结果；
- 在第一个真实压缩调用处暂停的工作；
- 尚在队列中的工作。

第一条输出跨越 Runtime 停止和部分销毁仍可独立解码，不被改写成取消。
其他三条只能各交付一次 `OWNER_STOPPED/CANCELLED`、没有业务载荷，
不能从清理线程冒充原网络所有者。最终四条完成计数恰好一次，未释放的
成功输出阻止预算外壳提前释放，最后引用归还后整体销毁成功。

## 构建与模块边界

扩展现有 `test_runtime_message_recovery`，不增加重复测试目标或生产翻译单元。
Xmake 只为该目标新增七个链接期包装：服务构造、Reactor 销毁和五个 pthread
同步对象操作。原有测试调用仍全部保留；故障定位限定到当前对象/真实销毁范围，
生产库不增加故障开关。SDK、协议、工作流、静态分析基线均未改动。

## 尚未覆盖

这是有限生命周期回归及一个独立释放缺陷修复，不是公开门面压缩接入。
仍需独立消息信封、方向性协商、网络信用、连接组 DATA 及 TLS 等任务。
生命周期仍要求外部串行化，不支持任意并发 free、强制线程终止或永久不合作工作；
预算不是整个 RSS、线程栈或内核资源的硬上限。本轮没有吞吐或尾延迟结论。

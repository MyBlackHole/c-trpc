## 结果

普通 V2 Client/Server 支持显式启用 TLS 1.3 required。每条连接的 TLS endpoint
由所属 Reactor 驱动；证书验证成功后才开始 Parser/HELLO 和 RPC 流量。TLS WANT
会更新 epoll 读写兴趣，TX 在 OpenSSL 成功接受明文字节前保持缓冲地址、长度和
代次不变。连接握手沿用已有绝对 deadline。普通 V2 的默认配置仍是明文；
transport-only/连接组在身份绑定交付前拒绝 TLS-required。

端到端用例覆盖 disabled 明文往返、TLS-required RPC 往返、每次转发 1–7 字节的
透明 TLS 代理、大消息、错误 CA、错误 SAN、TLS listener 拒绝明文、
transport-only 拒绝 required、明文 `sendmsg()` 快速路径，以及客户端和服务端
在显式排空后的 `close_notify`。认证失败路径不会进入业务处理器；disabled 路径
继续走原有 `recv()`/`sendmsg()`。

V2 请求方向通过 RPC `HALF_CLOSE` 收尾。若自定义对端在 RPC FINAL 前发送 TLS
`close_notify`，Reactor 会停止读取、排空当时已排队的控制/终局 TX，再完成本端有界
关闭；尚未产生 TX 的在途 RPC 按现有连接关闭策略终止。普通 V2 客户端只在等待 RPC
FINAL 与 Channel 排空后发送本端关闭告警。TLS `close_notify` 不替代 RPC 半关闭。

## 格式与静态分析

- 使用 clang-format 18.1.8；格式门禁自测 22/22 通过。按门禁逐行规则检查本次
  改动的 8 个 C/C++ 文件，0 处格式违规。整文件 dry-run 会报告仓库已有格式差异，
  因而本次只格式化并检查本次修改行。
- 格式脚本、GCC 分析器驱动/基线、Clang 分析器驱动/基线自测分别为
  22/22、12/12、12/12、10/10、14/14 通过。
- `check_compile_commands.py` 校验了 46 条真实 GCC Release 生产编译命令。
  GCC 16.2.1 对全部 46 个生产单元运行 `-fanalyzer` 后均生成对象；输出一条
  `analyzer-use-of-uninitialized-value` 诊断，位于未修改的
  `src/rpc/rpc_record_client.c:481`。为完成这次探索性全量运行，该检查被降为
  warning 并保留在构建日志中。
- 仓库的正式 GCC 分析器门禁固定 GCC 11；本机 GCC 16 未诊断门禁的泄漏负例，
  因此本地生产分析没有通过该门禁的负例/基线验证。没有将 GCC 16 结果与 GCC 11
  告警基线比较。本机 clang-tidy 23 与 CI 固定 clang-tidy 14 不同，未声称通过
  CI Clang 静态分析门禁。

## 未完成的边界

凭证异步获取/轮换、迟到凭证取消和组授权尚未实现；TLS-E 的 OpenSSL/内核完整

矩阵尚未验证。TLS profile 与 OpenSSL/内核分配尚未形成完整 `memory_budget_bytes`

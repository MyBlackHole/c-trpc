## 模块与静态链接边界

`runtime_message.h` 提供库内可选的分片消息启用、关闭、提交、取消和统计入口，
不公开可销毁的 MessageService 指针。每次 Runtime 成功启动后按分片显式启用，
没有修改公共配置或默认 Client/Server 行为。

`runtime_message_internal.h` 只供 Runtime 与具体消息适配使用：通过静态、只读、
有类型的 open/close 操作契约发布完整或失败保留的对象。Runtime 分片持有唯一
服务指针及其关闭责任；借用只存在于一个 owner turn 的内部适配调用，不暴露
Runtime 私有布局，也不能由消费者自行关闭父 Reactor 或直接释放服务。

具体绑定放在已有 `message_service.c` 对象中。`runtime.c` 不直接引用 Zstandard
或消息算法符号，未启用消息服务的静态 SDK 消费者不应因此被迫增加 Zstandard
链接依赖。实际安装消费端仍须由本次 CI 验证，不能仅根据模块图断言完成。
没有引入第二套执行器、队列或分配器；Xmake 构建定义无需新增生产翻译单元。

## 服务所有权与停止顺序

服务创建和启动在正确分片 owner 上执行。创建失败若没有发布对象，可释放绑定；
启动失败若保留了事件源、定时器或线程，Runtime 继续持有部分对象，后续 disable、
stop 或 destroy 负责重试。不能根据 enable 返回错误推断“没有资源需要回收”。

正常停止在原 owner 上关闭消息服务，内部继续使用既有有界完成交付、工作退出、
join、辅助源/定时器解绑和最终释放顺序。服务返回 AGAIN 或错误时，该分片的
父 Reactor 与旧执行资源不会继续停止；这保留了正常重试所需的所有者执行能力。
服务完整收敛后，才执行既有 Reactor 与 RPC 执行器停止路径。

正常 stop 成功后可再次 start，但不会自动复活旧服务。新轮次显式 enable，取得
新的服务/任务实例身份。旧任务能力不能影响新实例。

启用、关闭与 Runtime 生命周期 API 由外部串行协调，不承诺任意业务线程可以
同时修改分片服务绑定或销毁 Runtime。已接受的消息工作与完成交付可以在 stop
过程中运行，但调用者不得并发重新 enable。借用句柄不提供对象强引用保护。

## 输出比服务活得更久

Message 输出保留独立存储，但其预算地址属于 Runtime 分片。服务关闭和工作线程
退出不表示应用已释放全部输出。`tr_runtime_shard_release()` 在释放自身执行/对端
资源后检查该分片预算；非零时返回 AGAIN，保留整个分片数组和 Runtime 存储。

这允许先退役昂贵执行资源，随后由应用释放保留输出，再重试 destroy。
一旦 destroy 进入分片资源拆除，Runtime 标记为 retiring，不能把部分已经失去
Reactor 的对象重新 start。正常 stop 不设置这个终局标记，仍允许重新启动。

预算的零计数不是最后释放线程已经退出的证明。重试最终 destroy 前，外部必须
确认最后一次消息/令牌 release 已返回并排除并发业务与释放。此切片不提供预算
对象引用计数，也不把查询 current_bytes 当成通用并发静默屏障。

所有分片的预算原子在首次分配前统一初始化，包括构造未访问到的分片，保证
部分构造回滚读取预算时不是未初始化的原子对象。

## 新增验证场景

复用真实 `test_runtime` 目标，不增加测试二进制数量、不重复登记生产源。
新场景位于仅该测试包含的 `runtime_message_cases.h`，保持普通生产头的闭包。
旧场景全部保留；监听器重新打开的现有场景使用已支持的可选 NULL 端口输出。

1. **真实双分片消息生命周期**：每个分片启用实际 MessageService，提交真实
   Zstandard 编码，直接调用 Runtime stop 而不手动关闭服务或轮询结果。
   验证完成恰好一次、原 owner 交付及独立解码；正常重启后显式重新启用，旧任务
   能力被拒绝。保留输出使 destroy 返回 AGAIN，start 被拒绝；输出仍可读取和
   释放，最后重新 destroy 完成。
2. **预算压力与重试**：预约剩余预算模拟持续容量不足，enable 返回 AGAIN
   且没有发布子服务；释放预约后启用成功。disable 可重试且幂等，父 owner
   仍然响应，最终 Runtime 正常回收。预约不是实际分配同量载荷。
3. **父子生命周期故障契约**：真实 Runtime/Reactor 上注入一个受控、有类型的
   生命周期提供方。模拟部分 open 失败保留对象，close 分别返回 AGAIN、SYS
   再成功，验证 Runtime 保留预算与父 owner，最后正确回收。此场景不是实际
   Zstandard 分配失败、epoll 故障或父 Reactor 致命退出的复现。

运行测试中每次有限阶段重试设置单调时钟截止限制，失败返回不被当成成功；
不通过固定睡眠猜测工作或回调是否已经结束。

## 未完成的边界

父 Reactor 仍必须晚于消息服务关闭。若父循环先行异常退出，原 owner 调用失败，
本阶段保留 Runtime 和子服务，不伪装成已接管，也不保证此时可以最终回收。
下一阶段需要专用的父线程静默证明、完成责任接管与事件解绑协议，不能为了
让 destroy 返回成功就在其他线程执行原本约定 owner-only 的应用回调。

这是可选的库内 Runtime 入口接入，不是 Client/Server 默认网络消息入口；
尚无独立 RPC 信封、方向性算法协商、网络字节信用、大消息传输活性或 TLS。
现有 RPC 内嵌执行器没有迁移。异常接管未证明前禁止开启默认网络压缩。
本轮没有压缩或生命周期路径的性能结论，不关闭整体实现任务。

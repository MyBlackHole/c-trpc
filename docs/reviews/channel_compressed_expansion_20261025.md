# 小编码体大解码正文接收回归

日期：2026-10-25。版本：`2.0.0-dev.108 -> 2.0.0-dev.109`。关联 #241、#235、PR #324。

## 目标与场景

在真实 TCP Shared Channel 中补充压缩接收矩阵中的高扩张比正向场景：小编码体占用少量传输窗口，但服务端成功解码并交付较大的应用正文。该回归使用既有 Channel 压缩收发路径，不直接调用解码函数作为成功证据。

## 输入与断言

- 应用正文为 4,096 字节，逐字节填充 `0x5a`；Zstandard 编码体断言小于 64 字节。
- Channel 初始网络窗口为 128 字节；编码体加 16 字节 message envelope 小于窗口。实际发送后又检查客户端该消息的累计 TX wire 增量小于 128 字节。
- 使用 public `tr_message_builder` 创建正文并通过 `tr_stream_send_compressed` 发送。服务端真实 Channel 接收后，验证流和消息 ID、解码长度为 4,096 字节，并逐字节比较正文。
- 新场景纳入既有压缩接收测试序列，并调整后续接收计数及非法压缩消息拒绝断言，确保额外成功消息不会放松原负向覆盖。

## 验证结果

- GCC Release `test_transport/default` 连续 3/3 通过。
- 变更行 `git clang-format --diff HEAD -- tests/test_transport.c` 未发现格式改动；`git diff --check` 通过。
- 测试命令将 `TMPDIR` 与 `XMAKE_TMPDIR` 指向工作区 `build/test-tmp`；未在 `/tmp` 创建测试文件。

本次只扩展集成测试、记录与开发版本，不改生产运行时、公开 API/ABI 或 wire。它证明该 4 KiB 重复正文在当前压缩实现、单消息和 128 字节初始窗口下可用少于窗口的编码 wire 完成接收；不建立任意压缩输入的最大扩张比，也不等于大规模/RSS、分域/全局内存预算、恶意输入安全或跨机器稳定性验收。#241/#235 与 V2 整体验收仍保持开放。

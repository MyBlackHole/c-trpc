新增库内 `tr_server_create_record()`，声明位于

这使真实服务端监听、方法安装、业务执行、断连回收和终止销毁连成同一生命周期。

既有模块。新增代码负责组合根的配置、对象所有权和故障回滚，没有复制语义内核，
也没有增加另一种工作池、工作队列或独立的退役对象队列。`runtime.c` 未修改；
Runtime 对端槽只增加 V2 宿主指针及回滚关闭标记。

## 显式协议与应用契约

入口接收普通 Server 配置、内部调优、`tr_server_record_config` 和一张
`tr_rpc_dispatch_method` 表。方法描述、工作函数及参数指针在创建时复制并冻结；
原数组可以随即释放或修改，参数所指对象仍由调用者保持到 Server 销毁成功。

| 契约 | 本轮行为 |
| --- | --- |
| 线协议选择 | 该入口明确选择 V2 记录；不做 V1 自动协商或回退。 |
| 方法身份 | service/method 是不透明数字，允许零；相同二元身份拒绝重复。codec 要求非零，不增加 RAW 专属限制。 |
| 请求与工作 | 沿用 `tr_rpc_record_work_fn`，每调用按 FIFO 执行，不同调用可并发。正文和元数据由原派发器持有有界副本。 |
| 回复 | `reply` 只在当前工作函数内有效；追加条数、正文大小及总字节受既有派发配置限制。不能在回调返回后继续生产回复。 |
| 取消 | 协作式请求；参数、输入和生成的结果均须等已接受任务的完成责任收敛后才释放。 |
| 注册与拦截 | 方法表已冻结；旧 unary/stream 注册接口返回 `TR_ERR_UNSUPPORTED`。带 interceptor 或连接组能力的配置在创建时拒绝。 |
| 观测 | 内部诊断报告实际 peer、Channel、池和共享任务资源；稳定 RPC 语义统计返回 `TR_ERR_UNSUPPORTED`，保留输出不变。内部 V1 RPC 生命周期字段不解释为 V2 统计。 |

该头不进入安装 SDK。默认 `tr_server_create()`、公开 Client 创建和调用路径、
旧 `tr_rpc_call_handle` 及其发送、取消、元数据操作仍使用 V1。
V2 工作回调只取得数值调用身份，不把旧句柄伪装成新调用能力。
本轮也没有交付自定义初始/尾部响应元数据或长期异步生产者的应用接口。

成功创建后，`start` 只尝试一次；进入实际启动后失败的对象只允许继续销毁。
create 的正常失败保持 `*out == NULL`；构造回滚自身失败时保留部分 Server
所有权，调用者须继续 `destroy` 重试。同步生命周期操作由外部控制线程串行执行，
业务工作线程与 Reactor 回调内的自等待调用在状态修改前被拒绝。
`destroy` 及其重试使用同一个外部控制线程，以保持执行器进入最终销毁后，
同步原语销毁失败时所需的完成所有者身份。

## 全 Server 总额与每分片所有权

`record.tasks.workers`、`record.tasks.capacity` 和
`record.memory_budget_bytes` 均为全 Server 总额。对总额 T、分片数 N、
从零开始的分片 i，分配量为 `T / N + (i < T % N)`。每个分片至少有一个工作线程，
任务容量不得小于工作线程数；增加分片不会把同一总预算重复乘以分片数。
`record.endpoint` 是每对端宿主配置，调用容量还受 Server 的调用与 Stream 上限约束。

| 对象 | 所有者与释放责任 |
| --- | --- |
| Reactor、对端表、硬预算 | 由 RuntimeShard 持有；协议使用方、执行器和分片池完成释放后才销毁预算外壳。 |
| 通用任务执行器 | 每个 ServerShard 持有一个；在所属 Reactor 上创建、启动，供该分片所有 V2 对端借用。父线程 join 后由外部清理线程接管。 |
| V2 endpoint | 对端槽持有；借用 Channel、共享执行器和分片预算，自身完成清理后才允许释放这些依赖。 |
| 冻结方法表 | Server 持有，存储计入第一个分片的预算；全部端点与工作静默后释放。方法参数对象仍由应用拥有。 |

该入口不启用旧 `rpc_executor_group`、旧 RPC 消息池或 MessageService 的私有
执行器。旧内部调优中的 `executor_*` 和 `rpc_message_pool_count` 在此模式不使用；
任务资源完全由 `record.tasks` 配置。没有为了使用 NONE 记录而启动压缩线程。

硬预算覆盖已经参与 Runtime 记账的 Reactor、对端表、分片池、任务、方法表和
记录存储，不代表整个进程 RSS，也不包括线程栈、内核资源、业务自行分配的内存
及尚未纳入此预算的 Channel/Server 元数据。TX 正文或前缀可能比 endpoint
活得更久，不能仅因 endpoint 指针清空就释放预算所有者。

## 启动、断连和停止顺序

### 启动与接纳回滚

先启动 Runtime 的所有 Reactor，再在每个 owner 上创建并启动共享任务执行器，
注册分片回收定时器；这些步骤全部成功后才开放任何 TCP 接纳事件源。
因此后一分片工作线程启动失败时，前一分片不会已经开始接纳业务。
部分线程、定时器或事件源仍由原 Server 持有，失败回滚保留可重试状态。

接纳沿用原有数字 IPv4、TCP_NODELAY、握手总期限和 deferred Channel 流程。
方法与 V2 handler 安装成功后才启动 HELLO，避免客户端已经就绪而服务端尚未安装
记录处理器。接纳后续步骤失败时在 owner 上关闭精确连接，保留部分对端供后续
生命周期处理轮次清理；关闭自身失败也保留关闭标记，由同一回收路径重试。

### 正常断连与排空

断连通知唤醒已有分片 peer eventfd。任务完成通知也只写这个 eventfd，
不在执行器锁内调用应用代码或推进协议。每分片另用一个周期为 1ms..1s 的
既有 Reactor 定时器重试有界对端表，覆盖通知写失败或解绑暂时失败后的进度。

正常回收依次执行 endpoint 的 `close_on_owner()`、Channel 的
`detach_for_finalize()` 和 `finalize_detached()`。工作或解绑尚未静默时，
已断开的对端仍占原 peer 槽；完成后才清空槽位并累计回收数。
这会暂时减少可接纳容量，但不会把慢工作转移到无界退役列表。

Server 回收器不另行领取活跃 RPC 的完成；endpoint 继续通过自己的事件和
定时器，按照既有错误优先级推进完成与发送。断连 endpoint 的 close 复用同一
推进路径，发送背压不会重新执行业务。周期检查有明确成本，本轮没有性能结论。

`tr_server_drain()` 先停止接纳，再同步冻结回收定时器和 peer 事件，随后按既有
GOAWAY 与共享绝对期限等待 Stream 收敛。冻结保证外部排空遍历期间 peer 槽不会
被回收器清空；活跃 endpoint 自己的进度定时器继续工作。排空与终止销毁仍是
两个不同操作，destroy 不隐含优雅排空。

### 父线程停止后的统一回收

V2 destroy 先调用 `tr_runtime_stop()`，确认所有父 Reactor 已成功 join，再解绑
监听器、握手定时器、回收定时器和 peer 事件。真实事件循环致命退出也走这条
路径，不能在 join 之前把 `TR_ERR_CLOSED` 当成对象已可释放的证明。

每个分片的任务完成可能属于任意一个对端，因此回收顺序必须覆盖整个共享域：

1. 首轮遍历全部仍存活 endpoint，调用 `reap_stopped()` 进入清理域并请求取消。
   `TR_AGAIN` 表示该端点已经切换清理语义但仍有任务；任何其他错误都禁止随后
   领取这个共享执行器的完成。
2. 全部 endpoint 均完成上述切换后，统一 stop、adopt_cleanup、join 执行器，
   再有界 dispatch 完成。工作未退出或完成尚未交付完时返回 `TR_AGAIN`。
3. 第二轮 reap 释放 endpoint；清理通知使用 OWNER_STOPPED/CANCELLED，
   丢弃迟到成功载荷，不再向停止的网络发送。
4. 清除任务通知并销毁执行器，再释放 Channel、分片池和冻结方法表，最后销毁
   Runtime 及其预算外壳。执行器进入最终销毁后，失败重试只调用其 destroy。

任一步失败均保留尚有责任的对象。取消没有强制中断业务函数的能力，不能为了让
销毁返回成功而提前释放仍被工作线程使用的参数。已经被传输接受的 FINAL 也不
会撤销；`final_accepted` 始终只表示接受点，不是写出或对端收到的证明。

## 真实 Server 集成测试的 16 个顶层场景

新增 [`tests/test_server_record.c`](../../tests/test_server_record.c) 使用本机
真实 TCP。服务端完全由上述 `tr_server` 入口负责监听、接纳、调度和回收，
测试不手工 pump 服务端。客户端使用真实 Reactor、Channel 和既有 V2 Stream
绑定，socket 接管与 Channel 创建在同一次 owner 调用中完成，随后在
STREAM_OPEN_ACK 对应的 owner 回调中发出 OPEN；它尚不是公开
`tr_client` 的 V2 实现。

| 序号 | 顶层场景 | 直接保护的不变量 |
| --- | --- | --- |
| 1 | 构造配置 | 拒绝零/不足硬预算、少于 worker 数的任务容量、重复方法、interceptor，以及不能容纳最大方法正文及记录头的消息/窗口上限；配置拒绝断言 `*out == NULL`，不足预算明确返回错误并执行清理。 |
| 2 | 请求方向精确窗口边界 | 4097 字节请求正文加 48 字节头恰好等于服务端接收窗口和消息上限；OPEN 的信用实际归还后完成请求与回复。客户端接收窗口更大，不据此宣称双向等窗。 |
| 3 | 记录形状与槽复用 | 方法数组修改后冻结表仍有效；未知方法错误 FINAL 到达客户端且不执行业务，同连接后续合法调用成功；零条 MANY 请求/响应、零长度 ONE 消息及 4097 字节分片回复；`max_peers=1` 连续六轮回收。 |
| 4 | 两对端共享执行器与排空 | 两个真实对端的工作同时被冻结，只创建一个分片执行器；恢复后均成功，再通过真实 Server drain。容量不按对端重复计费。 |
| 5 | 断连时工作未静默 | 取消请求已观察到后，断开的对端仍占唯一槽位；工作释放后槽位回收，后续连接可正常调用。 |
| 6 | 正常停止时两个工作被冻结 | destroy 返回 AGAIN 且不销毁共享执行器；两个 endpoint 全部进入清理域后才交付完成，迟到成功不发给客户端。 |
| 7 | 真实 epoll_wait 致命失败 | 对服务端所属 epoll_wait 注入 EIO，使真实 Reactor 退出；仍按父 join 后的统一清理顺序收敛两个对端。 |
| 8 | 首轮第二个 endpoint 回收失败 | 在第二个对端进入清理域前返回 SYS，断言共享清理 dispatch 次数仍为零；重试通过全部清理屏障后才允许领取完成。 |
| 9 | 两分片正常运行 | 共创建两个执行器，总 worker 数为 3、任务容量为 16；多个真实连接和回收经过 Server 入口，合计资源不乘以分片数。 |
| 10 | 首分片部分工作线程启动失败 | 在真实任务启动过程的第 2 次 pthread_create 返回 EAGAIN，保留已建线程和对象供停止、销毁。 |
| 11 | 后一分片工作线程启动失败 | 在全 Server 第 3 次任务线程创建时失败，已成功的前一分片也参与统一回滚。 |
| 12 | 接纳时 endpoint 创建失败 | endpoint 创建边界返回 NOMEM；客户端仍存活时，服务端自行关闭失败连接、回收 peer，下一连接成功。 |
| 13 | endpoint start 部分发布失败 | 调用真实 start，待其已注册定时器后由 timer_arm 包装返回 SYS；服务端回滚真实已发布回调资源，客户端无需先退出。 |
| 14 | 正常断连的 handler 解绑失败 | 一次解绑 SYS 后保留 endpoint/peer；只靠服务端既有事件源和回收时钟重试，之后可复用槽位。 |
| 15 | 终止销毁的 handler 解绑失败 | destroy 返回 SYS 且保留 Server；再次销毁通过原有解绑屏障后收敛。 |
| 16 | 执行器 join 边界失败 | worker 已退出时 join 边界返回 SYS，执行器仍未销毁；外层重试完成剩余回收。 |

业务 MESSAGE 工作回调还实际调用 destroy、drain、start，确认三者返回 STATE，
并继续完成当前工作。停止场景故意在取消后继续生成成功回复，检查结果确实被清理。
每次 fixture 最后确认执行器创建/销毁计数配对、没有创建旧执行器组；客户端
资源也按其显式停止回收契约释放。

故障包装仅链接到新测试目标，正常支路调用真实实现。第 13 项是已注册定时器
之后的真实部分启动失败，不是绕过 start 的前置替身。第 12 项为明确的创建
边界拒绝，第 16 项为执行器 join 边界错误，不能据此宣称枚举了全部堆分配点或
真实 pthread_join 的所有失败条件。四种基数、端点错误优先级、独立 FINAL 背压等
更细的语义继续由已有记录/路由/派发/端点测试提供各自证据，不把它们重复计入这
16 个 Server 场景。

### TSan 暴露的测试客户端装配窗口

但 [TSan 作业](https://github.com/MyBlackHole/c-trpc/actions/runs/38989401658/job/117268173511)
的 `test_server_record` 在客户端 `tr_channel_create() == TR_OK` 断言失败。
完整归档日志没有 ThreadSanitizer 数据竞争报告，不能把普通 CHECK 失败写成
检查器检出数据竞争。本地原样检出该提交，连续定向运行的前五轮通过、第六轮
复现同一断言，首次失败即停止并保留全部日志。

外部 `tr_reactor_adopt_fd()` 成功仅表示接管命令已接受，连接可能在随后独立的
Channel 构造前处理到服务端关闭。接纳故障本来就要求服务端立即回滚，测试不能
假定这段间隙中的连接仍活跃。修正将 adopt 与 Channel 创建合并到同一次
`tr_reactor_call()`，adopt 成功即标记 fd 所有权转移；Channel 处理函数和定时器
全部安装后才允许 IO 分派。HELLO 在该轮次只进入发送队列。

修正仅改变测试装配顺序，保留原有成功断言、全部 16 个顶层场景、服务端主动
回收及失败重试检查；没有吞掉 CLOSED/STALE、延长等待或更改检查器配置。

修正提交 `38b1cd0e6a3b4e399d39c686e697602bbd6be6c9` 已重新验证新增测试：

## 大小、流控与迁移退出边界

在此入口，`limits.max_message_bytes` 是整条传输记录的上限。最大控制记录为
48 字节头加 512 字节元数据，因此本地消息上限与初始窗口都至少为 560 字节；
各方法最大请求、响应正文再加 48 字节，也必须同时不超过这两个本地上限。
检查使用宽整数计算，防止加上记录头后回绕。

这项保守准入及精确窗口测试不解决任意 `L > W` 的发送活性，也不替对端扩张其
接收窗口或消息上限。方向性能力协商、消息信用与网络信用重设计仍需独立推进。
本轮只使用 NONE，没有接入网络压缩、TLS、RPC 业务截止时间或慢 OPEN 的完整
调度策略；final_wait 是终局发送重试期限，不是业务执行期限。

旧 V1 路径暂时保留，是因为公开 Client 调用、旧句柄以及元数据、取消、拦截器和
统计契约尚未完成 V2 对等迁移。该状态不是永久维护两套端点或线程模型的目标。
后续继续在 #239、#240、#241、#242、#243、#248 的关联范围内完成以下退出工作，
各项按自身证据验收：

1. 确定稳定的 V2 应用回调与调用能力契约，覆盖长期异步生产者、初始/尾部
   元数据、取消、截止时间和完成交付域；弱句柄不承担并发 free 保护。
2. 将公开 Client 的创建、调用、发送/接收、排空和销毁接入同一 V2 记录链路，
   补齐两端门面之间的真实互操作测试，再明确默认协议选择与 SDK 迁移策略。
3. 在统一 Runtime 所有权下继续收敛旧 RPC 执行器及未来消息变换执行责任，
   复用现有通用执行器，避免为每个服务重新增加工作池或复制队列。
4. 新契约、调用方和失败回收完成迁移后，删除被替代的 V1 Endpoint、线协议和
   旧执行器路径；同时独立完成流控、网络压缩/TLS、统计和模块边界的未结任务。

本轮证明的是一个显式 V2 Server 实际入口及其有界生命周期，尚不构成完整
Client/Server 默认迁移、稳定 V2 SDK、全进程内存封顶或性能发布结论。

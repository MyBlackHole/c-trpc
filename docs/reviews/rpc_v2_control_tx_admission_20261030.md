# CONTROL TX 积压与发生器准入诊断

日期：2026-10-30；关联 #247、#241。延续[固定输入 RPC 对照](rpc_v2_reset_rpc_comparison_20261029.md)，
本轮定位到可运行 TX 的批次积压，并撤回证据不足的调度候选。18 个临时诊断场景仍全部
不满足原 clean 判定，40k RPC 容量继续未通过；生产源码、版本、池容量、线程数和测试入口均保持原状。

## 身份与观察范围

基线为 `a3077c32d449190eeb86b0cfb1b22918312da1f4`，生产代码等同 dev.182 的
`0d81342e85739bcd8ff0253bdbcd894c602696c0`。三个临时二进制按顺序各运行明文与
TLS/Zstd 的三个既有 profile，每格一次，共 18 场。原入口、40k 计划速率、250ms、
10000 次到达、16 个发生器、每个 64 槽/64 窗口及 3000ms 期限均保持不变。
仍是共享 x86_64 开发机、loopback、32 字节请求/响应和服务端工作延时零。
各场实际准入不同，三组顺序运行，不构成严格配对性能实验。

|---|---|---|
| 池基线 | 现有锁内按帧类型/主循环阶段计数；每 Reactor 至多八个首次失败快照；销毁时输出 | `3b244db25c40f3f6961aa40d5485a0cd3b8b2b124644c54f57ebffab6c386a70` |

| 准入基线 | 运行时不插桩；仅 bench 保存唤醒、取锁、API 入口/返回与终局时间，测量结束后输出 | `4131c2db443f001a980d4105ca32a9f8841fe7aed98197f3510a58ef30ec8c42` |

这些二进制含诊断成本，计数包含连接建立、预热、测量和排空，不能替代无插桩正式容量验收。

## 池满时发生了什么

池基线的六场都发生 CONTROL TX 池耗尽。23 个首次类型/阶段失败快照中，128 个
控制项全部仍在 owner 的发送队列里，普通命令队列数量均为零，Reactor 写重试等待
标志均为零；首次场景快照的待发连接数为 5–16。控制项类型只有
WINDOW_UPDATE 与 STREAM_CLOSE，部分快照 128 项全是初始信用通告。

原主循环在一批 RX 分派之后才统一推进 TX。Channel 收到 OPEN 时接受一个
WINDOW_UPDATE，RPC 结束后还需普通 CLOSE；多个连接的读帧先累积发送项。
这解释了快照中「池满、仍有可运行 TX、没有 socket 写等待」的组合。
失败计数落在 RX 和其后的定时器重试阶段，未观察到命令队列容量阻塞。
快照只覆盖每 Reactor 首次若干类型/阶段，不能推出每一次池耗尽都没有内核背压。

两组池诊断共 204 个 Server/Client 进程的所有池在销毁时 free=capacity，按帧类型
汇总的取得/归还数量一致。这证明这些运行最终归还了池项，不证明运行中从未滞留，
也不代表 OpenSSL、RSS 或全局预算已经验收。

## 调度候选为何没有采用

下表每格为「已接受调用数 / CONTROL TX 耗尽次数」。池容量均为 128；没有增加
线程、调用窗口或发送项数量。两种传输的 small/default/large 对应原 call limit
32/128/256，完整错误与丢弃均保留在账本。

| 传输 | call limit | 池基线 | RX/TX 分派候选 |
|---|---:|---:|---:|
| plain | 32 | 1992 / 3415 | 1962 / 166 |
| plain | 128 | 2321 / 1229 | 1549 / 0 |
| plain | 256 | 2136 / 853 | 1900 / 1 |
| TLS/Zstd | 32 | 1560 / 3752 | 1465 / 1531 |
| TLS/Zstd | 128 | 1502 / 2873 | 1025 / 0 |
| TLS/Zstd | 256 | 1365 / 67 | 1319 / 0 |

2026-10-30 校注：本表 call limit 栏实际为基准 --capacity 参数；configure_limits
设置的 max_calls/max_streams 为其两倍。原字段与结果保留，见[后续追踪的输入说明](rpc_v2_rpc_progress_trace_20261030.md#输入与身份)。

候选三场不再触发控制池耗尽，但六场仍全有发生器丢弃/迟到，实际准入也下降；
TLS small 场景还有 371 次 DATA 池耗尽及 91 次 deadline。单次共享主机运行不能
证明这些新增现象由候选引起，同样不能把更小的控制池计数当作性能改进。
候选已撤回，待进一步定位完整调用等待与工作配额后再决定调度改动。

## 发生器的槽位为何不足

准入基线另做六场，保存 60000 条计划到达记录。49110 次 scheduler_dropped
全部可由已接受调用的入口/终局时间重建为：取锁时 64 项仍未终结；没有发现
「已有空槽却丢弃」的反例。10890 次实际提交全部接受并完成，10857 次 OK，
其余 33 次为 RESOURCE_EXHAUSTED；仍不是 60000 次实际网络到达。

以下分位数合并同场 16 个发生器的原始样本，使用 nearest-rank，单位微秒。
它与原输出使用的聚合方式分别保存，没有改动原判定。

| 传输 | call limit | 取锁等待 P99 | 同步提交 API P99 | API 入口至终局 P50 / P99 |
|---|---:|---:|---:|---:|
| plain | 32 | 3.213 | 1132.349 | 175217.384 / 326499.405 |
| plain | 128 | 3.352 | 1111.048 | 148925.061 / 208117.672 |
| plain | 256 | 3.352 | 1357.660 | 116690.156 / 295509.573 |
| TLS/Zstd | 32 | 2.863 | 919.191 | 232102.202 / 355578.491 |
| TLS/Zstd | 128 | 3.422 | 1186.757 | 189426.258 / 344292.292 |
| TLS/Zstd | 256 | 2.864 | 1170.902 | 176658.501 / 343506.147 |

取锁至 API 入口的准备 P99 为 4.75–9.149us，包含原 64 槽扫描和正文准备。
单次 API 耗时超过发生器 400us 间隔的调用为每场 63–196 个，不能忽略其对迟到的
影响；公开 unary 入口经原同步 owner 调用提交。这些记录显示长期占槽的终局等待
明显长于本地取锁/准备。终局等待仍包含 Client owner、传输、Server 调度、工作及
回包，尚不能把 117–232ms 的中位数归给其中某一层。

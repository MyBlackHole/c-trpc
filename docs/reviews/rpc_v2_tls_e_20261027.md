## 本次范围

`test_tls_gnutls_interop` 现在覆盖两个方向：

- 独立 `gnutls-cli` 进程连接公开 V2 TLS-required Server。限定 TLS 1.3，Server 强制 mTLS；验证可信身份成功、缺少客户端证书和错误服务端 DNS 名被拒绝。此方向只完成 TLS 握手，不发送 TRP/RPC 帧。
- c-trpc V2 Client 连接由 GnuTLS TLS API 驱动的本地 TLS terminator。Server 限定 TLS 1.3，要求客户端证书并由 GnuTLS 验证证书链；握手后将解密出的 TCP 字节透明转发到本地明文 c-trpc V2 Server。Client 执行 RAW unary，发送 4 字节正文；Server 回显原正文，Client 验证单条回复正文完全一致且终局为 OK。此用例证明真实 RPC 正文通过外部 GnuTLS TLS 实现往返，不再止于 HELLO/ACK。
- 该 GnuTLS 端点只终止 TLS 并透明代理到本地 c-trpc RPC Server，不实现 TRP/RPC 服务端协议。因此它不证明独立 GnuTLS RPC 实现与 c-trpc 的协议互通，也不替代独立业务进程/公网网络矩阵。
- c-trpc Client 的错误服务器名与无客户端证书用例均不能完成 TLS 握手，`tr_client_connect()` 及时返回 `TR_ERR_CLOSED`。GnuTLS Server 对无证书路径报告 `GNUTLS_E_CERTIFICATE_REQUIRED`。

新增回归同时修复一个等待终态错误：TLS 失败关闭 Reactor 连接并唤醒 Channel 等待者后，若没有重连任务，`tr_channel_wait_ready_deadline()` 现在返回 `TR_ERR_CLOSED`，不再把已关闭连接继续等到原始 deadline 并误报 `TR_ERR_TIMEOUT`。启用重连时仍允许等待下一次就绪。

身份文件沿用现有 helper，写入 worktree 的 `build/test-tmp/`。用例不通过 shell 启动子命令；独立 `gnutls-cli` 使用 `posix_spawnp()` 固定参数。反向 Server 使用 GnuTLS API 和独立线程。新增构建依赖为系统 `libgnutls28-dev`；CI 同时安装 `gnutls-bin` 与该开发包。测试身份文件、缓存与构建产物均留在工作区 `build/`，未写入 `/tmp`。

## 本地验证

本机：GCC、Clang 23.1.4、OpenSSL 3.6.5、GnuTLS 3.8.13、Xmake 3.1.2。所有 Xmake 命令将 `TMPDIR`、`XMAKE_TMPDIR` 指向 worktree 的 `build/`。

| 验证 | 结果 | 用时 |
| --- | ---: | ---: |
| GCC Release 互通目标 | 1/1 通过 | 0.736 秒 |
| Clang 23 Release 互通目标 | 1/1 通过 | 0.979 秒 |
| GCC ASan/UBSan 互通目标（泄漏检查开启） | 1/1 通过 | 0.927 秒 |
| GCC TSan 互通目标 | 1/1 通过；同一二进制再连续运行 5/5 通过 | 0.971 秒 |
| GCC ASan/UBSan 全量套件 | 91/91 通过 | 106.252 秒 |

CI 使用 Ubuntu 22.04 的 GnuTLS 3.7.3。dev.24 和 dev.25 的 14 项检查中其余 13 项通过，但 ASan/UBSan 均报告同一条 52 字节泄漏。dev.25 慢速分配回溯确认来源是 `argz_add_sep` → `newlocale` → `libp11-kit.so.0` → 动态加载器 `_dl_init`，没有项目代码帧；在测试入口关闭 PKCS#11 自动发现也无法阻止 DSO 构造函数。dev.26 加入 `tests/lsan.supp`，只抑制包含 `libp11-kit.so.0` 的堆栈，`detect_leaks=1` 仍开启；首次 CI 运行发现 Xmake 在目标工作目录执行测试，故相对路径被解析到 `build/linux/x86_64/asan/tests/lsan.supp` 而不存在。dev.27 将 suppression 路径改为 `${{ github.workspace }}/tests/lsan.supp`；CI 日志确认抑制命中一次、52 字节，dev.27 全部 14 项检查通过。此 suppression 会隐藏该库栈上的其他泄漏，因此本测试不调用 PKCS#11 API；dev.28 CI 结果以 PR #312 实时检查为准。

## 尚未覆盖

本次不证明 OpenSSL 堆、证书解析峰值和内核 socket 缓冲的完整硬预算；不覆盖并发握手洪峰/取消、长期负载、性能回归、目标平台矩阵或公网发布安全门槛。应用级 RPC 正文通过 GnuTLS TLS 端点转发到本地 c-trpc Server；尚未覆盖独立外部 RPC 服务端实现、跨进程业务负载及目标网络性能。

因此 TLS-E 与 #234 仍未完成，PR #312 保持未合并；本记录只描述 dev.28 候选包含的双向 TLS、RPC 正文互通、等待错误修正和 LSan 配置路径修正，不代表 TLS-E、#234 或 V2 整体验收完成。

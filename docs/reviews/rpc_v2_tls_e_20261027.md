## 本次范围

`test_tls_gnutls_interop` 现在覆盖两个方向：

- 独立 `gnutls-cli` 进程连接公开 V2 TLS-required Server。限定 TLS 1.3，Server 强制 mTLS；验证可信身份成功、缺少客户端证书和错误服务端 DNS 名被拒绝。此方向只完成 TLS 握手，不发送 TRP/RPC 帧。
- c-trpc V2 Client 连接由独立 GnuTLS TLS API 驱动的本地 Server 线程。Server 限定 TLS 1.3，要求客户端证书并由 GnuTLS 验证证书链；随后收取并回显真实 TRP1 HELLO，再收取并核对 Client 的 HELLO_ACK。成功用例证明 TLS 互通和 Channel 就绪协商已完成，不代表 RPC 方法调用互通。
- c-trpc Client 的错误服务器名与无客户端证书用例均不能完成 TLS 握手，`tr_client_connect()` 及时返回 `TR_ERR_CLOSED`。GnuTLS Server 对无证书路径报告 `GNUTLS_E_CERTIFICATE_REQUIRED`。

新增回归同时修复一个等待终态错误：TLS 失败关闭 Reactor 连接并唤醒 Channel 等待者后，若没有重连任务，`tr_channel_wait_ready_deadline()` 现在返回 `TR_ERR_CLOSED`，不再把已关闭连接继续等到原始 deadline 并误报 `TR_ERR_TIMEOUT`。启用重连时仍允许等待下一次就绪。

身份文件沿用现有 helper，写入 worktree 的 `build/test-tmp/`。用例不通过 shell 启动子命令；独立 `gnutls-cli` 使用 `posix_spawnp()` 固定参数。反向 Server 使用 GnuTLS API 和独立线程。该夹具只读取 PEM 身份，因此显式以 `GNUTLS_PKCS11_FLAG_MANUAL` 初始化 GnuTLS，不加载宿主 PKCS#11 模块。新增构建依赖为系统 `libgnutls28-dev`；CI 同时安装 `gnutls-bin` 与该开发包。测试身份文件、缓存与构建产物均留在工作区 `build/`，未写入 `/tmp`。

## 本地验证

本机：GCC、Clang 23.1.4、OpenSSL 3.6.5、GnuTLS 3.8.13、Xmake 3.1.2。所有 Xmake 命令将 `TMPDIR`、`XMAKE_TMPDIR` 指向 worktree 的 `build/`。

| 验证 | 结果 | 用时 |
| --- | ---: | ---: |
| GCC Release 互通目标 | 1/1 通过 | 0.530 秒 |
| Clang 23 Release 互通目标 | 1/1 通过 | 0.489 秒 |
| GCC ASan/UBSan（泄漏检查开启） | 1/1 通过 | 0.479 秒 |
| GCC TSan | 1/1 通过 | 0.536 秒 |

CI 使用 Ubuntu 22.04 的 GnuTLS 3.7.3。dev.24 的 14 项检查中，ASan/UBSan 在该互通进程报告 52 字节由 glibc `argz_add_sep` 分配的泄漏，其余 13 项通过。dev.25 显式关闭宿主 PKCS#11 provider 自动发现，以隔离只依赖 PEM 文件的测试；当前 head 的 CI 结果以 PR #312 实时检查为准。

## 尚未覆盖

本次不证明 OpenSSL 堆、证书解析峰值和内核 socket 缓冲的完整硬预算；不覆盖并发握手洪峰/取消、长期负载、性能回归、目标平台矩阵或公网发布安全门槛。c-trpc Client 到 GnuTLS Server 的应用测试止于 HELLO/ACK，没有执行 RPC 方法或传送 RPC 业务数据。

因此 TLS-E 与 #234 仍未完成，PR #312 保持未合并；本记录只描述 dev.25 的互通和等待错误修正，不代表 TLS-E、#234 或 V2 整体验收完成。

# V2 Channel 固定存储预算评估

日期：2026-10-23。基线 `d1a5c12dee226c96b61179dfd9a4467e60055275`
（2.0.0-dev.5）；本次版本 2.0.0-dev.6。对应 [#241](https://github.com/MyBlackHole/c-trpc/issues/241)。

## 问题与修复

普通 V2 的 Reactor、RPC 对象和消息缓冲区已经使用所属 shard 的
`tr_memory_budget`。Channel 对象、流槽与终止记录共用数组、流索引则直接
`calloc`，创建多个连接时这部分固定存储未计入共享预算。它受配置的最大流数
和连接数限制，不属于无界队列；缺口在于预算不能准确反映实际占用。

Channel 创建前先归一化并验证配置，计算三块固定存储的请求字节数，执行
溢出检查，然后一次性预留预算。预留失败返回 `TR_AGAIN`，不分配 Channel，
也不发布反应器处理函数。构造中途失败，自动清理在释放存储后归还预算；
创建失败但回调仍可能持有对象时，预算随部分对象保留，直到成功销毁。
正常销毁与服务端 detached 收尾复用同一归还函数。

普通 Client 和 V2 Server 将 Channel 指向已有的 shard 预算；内部独立
Channel 未配置预算时仍可运行。三块存储分别按实际申请字节记账，重组池
及消息缓冲仍由原有预算路径承担，不重复计入。预算对象必须存活到最终收尾。

## 验证

- 修复前新增共享预算回归实际失败：Channel 创建成功后 `current_bytes==0`。
- 修复后两个 Channel 共用预算：首个成功，预算恰好容纳一个时第二个
  在分配前返回 `TR_AGAIN`；销毁首个后第二个可以创建，末尾账目为零。
- 定时器发布失败时构造归零；回调解绑失败导致部分对象保留时继续计费，
  重试销毁成功后归零。复杂构造故障测试更新了无效配置在分配前拒绝的
  调用次数断言，并验证故障注入仍实际命中。
- GCC release 全量 `xmake test -v -j1`：80/80 通过。
- GCC ASan/UBSan：构造事务、复杂故障注入、普通 V2 Server、服务端
  Record、V2 Client Record、公开 V2 SDK 六个目标 6/6 通过；启用 leak
  检测和错误立即退出。

GCC 11 静态分析仍报告原有的协议 HELLO 缓冲逃逸诊断：文件、检查类别、
列与消息完全相同，仅因本次文件前部增加两行而从 700:9 移至 702:9。
该路径未修改，既有[所有权审查](release_static_risk_review_20261018.md)
仍适用；精确告警基线仅更新坐标，保留 `unverified` 状态，不新增豁免。
Clang 14 在旧候选的 43 个生产单元中从 9 条降为 8 条，消失的是旧
`build.channel` 在非法配置返回时的潜在泄漏报告。本次将配置验证移到
分配之前，该失败分支不再拥有 Channel；故障注入已核对零分配，其他
构造回滚仍由 `TR_AUTO` 清理。精确基线移除该条观察记录，剩余 8 条
继续 `unverified`；告警消失本身不代表所有所有权路径都已证明。

固定存储只有创建和销毁时的一次原子预算操作，收发消息路径没有新增分配
或预算操作。未测量吞吐、尾延迟或 40k 连接容量，不能推导性能目标达成。

这次只修复 #241 的 Channel 固定存储账目。压缩/解压、慢消费者、
多 DATA 及跨 shard 全局预算与完整逐步账本仍需另行实现和验证。

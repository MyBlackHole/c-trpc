# PERF-V2-01：初始信用背压恢复与容量边界

日期：2026-10-23。版本：`2.0.0-dev.2`。沿原 [#247 登记](https://github.com/MyBlackHole/c-trpc/issues/247#issuecomment-6355445570) 实施，关联 [#241](https://github.com/MyBlackHole/c-trpc/issues/241)。
代码固定点：[`b961701a0ed14b7677f13f8cc366ce21080eaba3`](https://github.com/MyBlackHole/c-trpc/commit/b961701a0ed14b7677f13f8cc366ce21080eaba3)。基线：`49bd7e8a857275f64c462ace44085e5a4fe9b9cb`，其生产代码与 R17 使用的 `dd3332ee` 一致。

## 结论与根因

本次修复了初始 `WINDOW_UPDATE` 遇到控制 TX 池暂满后错误地中止整个连接的问题。没有完成 40k 吞吐验收，也没有消除流槽位容量限制。原 [R17 评估](rpc_v2_release_boundary_20261023.md) 及 CI 负结果保持为历史证据。

本地先用原有脚本重现三个容量档各三次，9/9 都出现控制池耗尽、提交错误和 unavailable。另行使用 GDB 作归因；调试运行不参与性能比较：

1. 首次失败时控制池容量 128、空闲 0、耗尽事件 1。
2. `tr_channel_handle_stream_open()` 的初始信用发送返回 `TR_AGAIN`，经 `tr_channel_protocol_error()` 转成 `TR_ERR_STATE` 中止精确连接代次，连带终止其他流。
3. 客户端首次后续提交错误为 `TR_ERR_CLOSED (-13)`。这与应用收到的 unavailable 是不同层次的计数。
4. 已有流的消费信用原有重试机制没有覆盖初始确认，不能由“已有 WINDOW_UPDATE 重试”推断新流也能恢复。

## 处置与不变量

- 每条物理连接最多保留一个 `ACCEPTING` 流，继续使用已有流槽。它尚未交付 `OPENED`，也尚未推进受理高水位。
- 仅暂停该连接继续接收；TX 和其他物理连接仍能前进。协议暂停独立于缓冲池暂停，普通 `RESUME_RX` 不得提前解除。
- 由既有维护定时器重试初始信用，沿用 25ms 周期。只有取得发送责任后，才推进高水位、解除暂停并通知上层；后来的 OPEN 不能越过前者。
- 本地排空冻结 cutoff 后拒绝未确认流，释放其槽并恢复接收，以便读取对端 GOAWAY。不得在 GOAWAY 后补发该流信用。普通销毁与服务端解绑都归还借用连接的 RX。
- 无法登记重试定时器时明确中止，不能留下永久暂停；没有空闲流槽时维持现有容量失败策略。没有增加默认池、无界队列、线程、公开 API、协议字节或调用重放。

本机 x86_64 的固定状态大小：Connection 752 → 760 字节，Channel 984 → 1016 字节。接收热路径增加暂停判断，压力时多一次暂停/恢复的 epoll 更新。25ms 是维护周期，不是实际恢复延迟的保证；调度、池再次占满及串行积压都可能使等待更长。

## 同配置性能比较

环境：AMD Ryzen 7 PRO 4750U，Linux 7.2.11、glibc 2.44，CPU affinity 0–15；GCC release、自动 CRC、TCP IPv4 loopback、V2 schema 2。此环境与 R17 的共享 CI runner 不同，因此只比较下面这对本地运行，不把它与 R17 的吞吐数字拼接。

每档三次，每次 offered 10,000、计划到达率 40,000/s、16 个发生器、每个 window/capacity 64、总 warmup 32、超时 3 秒。三个脚本 `capacity` 值为 32/128/256；`bench_rpc.c` 实际设置 `max_streams = max_calls = 2 × capacity`，故对应每连接流上限为 64/256/512。`bulk_bytes` 分别为 16/64/64 KiB，门面的消息上限为 `bulk_bytes + 512` 字节，初始信用为该上限的四倍。所有前后配置一致。

资源列均为三次中位数。**P99 指标是每次取 16 个发生器成功调用 P99 的最大值，再取三次中位数，不是合并样本的全局 P99。** 现有脚本没有保留全部延迟样本，不能据此构造全局分位数。服务端 CPU/RSS 包含启动、warmup 和 drain；发生器 RSS 是各进程峰值之和，不是同时采样的总峰值，也不是协议内存预算。

默认及大档 6/6 样本的受理调用全部成功结束；压力信号和发生器丢弃仍然存在，clean 仍为 0/3。恢复后调用不再因连接中止提前释放，发生器在途槽占用更久，丢弃和成功调用延迟明显上升。故这证明连接恢复语义改善，**不证明达到 40k、有足够容量或延迟达标**。

所有 18 个前后样本均满足 offered = dropped + attempted、attempted = accepted + submit_errors + submit_again，以及受理/终局账本收敛。所有样本 deadline、resource_exhausted、invalid_responses 和 submit_again 均为零；服务器 started = finished、queued = running = 0，16 个 peer 全部回收，drain 成功。

### 小档剩余失败

修复后另一次 GDB 归因捕获 `active_streams = max_streams = 64`，控制池仍有 5/128 个空位；新 OPEN 分配槽失败，按既有策略转为 `TR_ERR_NOMEM (-2)` 中止连接。它是有限流槽的明确容量失败，不是本次已修复的初始信用重试丢失。此调试样本也不参与上表。

## 验证与审查

- 先建立真实池耗尽回归：旧代码在“连接 DOWN 必须为零”的断言失败。新增拆除回归也先证实会遗留 RX 暂停，再修复。
- `test_channel_drain` 15 组通过：共享/拆分连接、其他连接进展、旧流恢复、初始确认 FIFO、槽位复用、普通 RESUME_RX、禁用保活、排空及两种拆除路径。
- `test_stream_reset` 保留流槽耗尽的失败断言，并验证信用恢复后正常 RESET、重试定时器失败时收尾。
- 本地 GCC release 全套 **79/79**；上述两个压力/生命周期目标在 GCC ASan/UBSan 下通过；clang-format 18.1.8 检查 5 个修改源码文件，0 失败。
- 候选 CI 的两个静态分析器均完整扫描 43 个生产单元，仍为 GCC 11 的 1 条、Clang 14 的 9 条未裁定诊断。实际工件确认仅三处既有位置移动：GCC Channel 687 → 695；Clang Reactor 320 → 322、Channel 3275 → 3359。核对原语句和完整诊断后更新位置，`review_state` 继续为 `unverified`，不宣称误报或修复。
- 审查由当前主会话按 `code-review-checklist` 完成，检查状态责任、锁/回调边界、错误清理、流代次、GOAWAY 高水位、原子快照、容量和公开兼容面。**没有使用子 agent，不冒充独立审查。**
- 候选及实际主线的 GitHub CI、benchmark smoke、诊断工件与最终状态在原 #247 登记中补充；本文件不提前声明尚未运行的远程检查。

CI 的 11 个 job 统一设置 `TMPDIR` 和 `XMAKE_TMPDIR` 为其既有 `runner.temp` 输出目录；本地使用工作区 `build/test-tmp`。未改检查标识或测试参数。

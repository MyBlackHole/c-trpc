# Shared Channel 四存活压缩流六轮公平性回归

日期：2026-10-25。版本：`2.0.0-dev.100 -> 2.0.0-dev.101`。关联 #241、#235、PR #324。

## 目标与场景

延长 dev.100 的真实 TCP Shared Channel DATA TX 池恢复场景，给持续有数据可发的四个压缩
Stream 建立可重复检查的帧轮转边界。测试使用容量为 1 的 DATA TX 池和 128 字节帧上限；BULK
RAW Stream 在 socket `EAGAIN` 时占用唯一池项。准备 RESET 的 BULK 压缩候选先被确认确实遇到
池满并登记 DATA TX 就绪等待，再提交四个存活压缩 Stream。RESET 候选后解除 socket 阻塞。

## 调度断言

- 最初四个成功压缩 DATA 帧分别属于四个不同的存活 Stream，且均为 FIRST、非 LAST。
- 紧随其后的 20 个续帧按这四个 Stream 的既定顺序轮转五轮；每条仍可发送的流再次获得机会前，
  其余三条均各发送一次。
- RESET 候选没有 DATA；四条压缩正文和 RAW 正文逐字节交付；消息数正确；TX 池和消息预算归零。

该边界表示本测试固定四个持续可发送者时的六轮帧级调度，不是通用等待时间、吞吐或跨机器 SLA。

## 验证结果

- GCC Release `test_transport/default` 连续 6/6 通过；每次均检查 24 个帧记录，场景观察到 40 次池满重试。
- GCC Release 项目全量测试 91/91 通过，耗时 148.053 秒。
- clang-format 23.1.3 变更行检查和 `git diff --check` 通过。当前 clang-format 23 对该历史测试文件整文件格式检查会报告未修改代码的格式差异，因此只检查变更行。
- 局部调度游标变异（成功发送后错误地停留在同一 Stream）导致新回归按预期失败；恢复原生产代码后，连续 6/6 和全量测试通过。

本次只扩展测试、文档和开发版本号，不改生产运行时、公开 API/ABI 或 wire。尚未建立五条及以上存活流、长期持续注入、逐消息等待上界、吞吐阈值、跨机器基线或完整预算/取消矩阵；#241/#235 与 V2 整体验收仍开放。

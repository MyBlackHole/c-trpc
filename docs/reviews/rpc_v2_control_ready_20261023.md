# PERF-V2-02：按控制发送容量恢复初始信用

日期：2026-10-23。版本：`2.0.0-dev.3`。沿 [#247 登记](https://github.com/MyBlackHole/c-trpc/issues/247#issuecomment-6357116644) 实施，关联 [#241](https://github.com/MyBlackHole/c-trpc/issues/241)。
基线：`36dadcc298a3606c87a36f1b430e0a94107e52a2`（`.dev.2`）；产品提交：[`bd3855b901891cd4f0091a31b33bc0f98b3fa37d`](https://github.com/MyBlackHole/c-trpc/commit/bd3855b901891cd4f0091a31b33bc0f98b3fa37d)。

## 结论与边界

初始 WINDOW_UPDATE 暂满后的恢复现在能由实际发送容量触发，无需等待 25ms 维护定时器。定时器仍承担兜底责任。本轮证明了容量通知、FIFO、预算及生命周期语义；**不证明所有容量档性能改善或 40k 达标**。

本地默认档和大档的成功 P99 指标下降，受理调用全部成功结束；小档的提交错误和 unavailable 增多，成功总数下降。该负结果必须保留：更快确认改变了受理节奏，原有流槽满即中止连接的策略仍会连带失败。后续必须单独处理有限流槽准入，不能用扩大默认池或隐藏小档样本替代。

## 实现与责任

- 每连接内嵌一个一次性等待项，所有者维护 FIFO 链，重复登记不改变位置；不分配额外请求表、不扫描全部连接。
- 控制池和命令队列均有容量时才通知。通知是就绪观察，不预留资源；竞争失败者重新排到队尾。
- 通知只在 Reactor 调度点执行，先摘除再回调，共用每轮 TX 分派预算。容量归还和登记函数内部都不回调 Channel。
- 生产者跨线程归还控制池的首个空位时，通过既有 eventfd 唤醒所有者。池锁串行化发布与容量检查，覆盖检查后入睡的交错。
- 关闭精确连接代次、替换处理器或显式取消都会摘除观察。Channel 确认成功、排空拒绝和拆除均取消观察并归还 RX 暂停。
- 保留每物理连接最多一个待确认流、初始确认后才推进受理高水位、GOAWAY cutoff、普通 RESUME_RX 不越过协议暂停，以及兜底定时器设置失败时明确收尾的契约。

公开 API、协议字节、默认容量和流槽满策略未变化。本机 x86_64 固定状态：Connection 760 → 776 字节，Reactor 2544 → 2584 字节，Channel 1016 字节不变；内存预算仍按实际 `sizeof` 计入。无观察者时只有空链判断；有观察者时在已有互斥锁下检查池与命令容量。

## 同配置测量

AMD Ryzen 7 PRO 4750U，Linux 7.2.11、glibc 2.44，affinity 0–15，GCC release、自动 CRC、TCP IPv4 loopback、V2 schema 2。前后均运行三个容量档各三次：每次计划 40,000/s、offered 10,000，16 个发生器、每个 window/capacity 64、warmup 总数 32、timeout 3 秒。脚本容量 32/128/256 实际对应每连接 `max_streams=max_calls=64/256/512`；消息与初始信用参数和 [PERF-V2-01](rpc_v2_control_tx_pressure_20261023.md) 一致。

计数为三次合计，每档 offered 均为 30,000；吞吐为三次中位数。

**成功 P99 指标：每次取 16 个发生器成功调用 P99 的最大值，再取三次中位数，不是合并样本的全局 P99。** 小档较低延迟与 CPU 伴随更少成功请求，不能解释为整体收益。固定到达窗口中，成功完成率和成功总数也不是同一指标。

三档的服务端峰值 RSS 中位数均为 27,212 → 27,180 KiB；发生器峰值 RSS 合计中位数均为 435,392 → 434,880 KiB。RSS 是进程高水位，发生器列为各自峰值之和；CPU/RSS 包含启动、warmup 与 drain，不是协议内存预算或每次调用成本。

所有 18 个样本均满足到达、提交、受理终局、服务端任务及 peer 账本收敛。deadline、resource_exhausted、invalid_responses 和 submit_again 均为零；16 个 peer 全部回收，drain 成功。所有档位仍为 clean 0/3，发生器延迟/丢弃和控制池压力仍存在；修复版默认/大档各有一次 DATA TX 池压力，不能把单项延迟变化描述为消除了系统压力。

### 小档错误归因

另一次 GDB 运行捕获首个协议错误：`TR_ERR_NOMEM (-2)`，`active_streams=max_streams=64`，控制池仍有 `8/128` 空位，调用栈为 `tr_channel_handle_stream_open()` 分配流槽失败后进入 `tr_channel_protocol_error()`。此运行只用于归因，未混入性能样本。它证实仍然存在流槽容量墙；三个样本不能精确拆分调度变化与环境波动对退化幅度的贡献。

## 验证与审查

- RED：延后真实兜底定时器 60 秒，解除真实控制池发送压力；旧实现等待初始信用 5 秒后断言失败。修复版在相同故障注入下恢复，未用“耗时小于 25ms”作为易抖动断言。
- `test_channel_drain` 17 组：共享/拆分连接、定时器兜底与容量恢复、其他连接 DATA、初始确认 FIFO、代次复用、排空、解绑和销毁。
- 新 `test_reactor_control_ready` 8 组：共享池跨连接公平性、重复登记、取消、处理器替换、槽位复用、跨线程唯一唤醒、无 I/O 重登记、命令队列满，以及 70 个连接跨轮次遵守 64 次分派上限。部分组覆盖多个关联不变量。
- GCC release 全量 80/80；补充的最终 70 连接场景单独通过；Channel、控制通知和 RESET 三个目标的 GCC ASan/UBSan 3/3。clang-format 18.1.8 检查 6 个修改源码，0 失败。
- 主会话按 `code-review-checklist` 检查正确性、锁顺序、代次/回调寿命、错误清理、容量、热路径开销、测试与范围。没有子 agent，也不冒充独立审查。
- 候选与实际主线 CI 的最终结果、静态分析位置核对和分支清理在 [#247 登记](https://github.com/MyBlackHole/c-trpc/issues/247#issuecomment-6357116644) 补充；本地通过不代替尚未完成的远程验证。

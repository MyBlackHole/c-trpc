# Shared Channel 六存活压缩流六轮公平性回归

日期：2026-10-25。版本：`2.0.0-dev.101 -> 2.0.0-dev.102`。关联 #241、#235、PR #324。

## 目标与场景

在真实 TCP Shared Channel DATA TX 池恢复场景中，将持续有数据可发的压缩 Stream 从四条扩到六条，
检查公平轮转是否跨更多 Stream 槽位保持稳定。Channel 配置八个 Stream 槽，其中一个 BULK RAW
Stream 在 socket `EAGAIN` 时占用唯一 DATA TX 项，一个 BULK 压缩候选在确认遇到池满并登记 DATA TX
就绪观察后被 RESET，剩余 CONTROL/BULK 各三条压缩 Stream 等待恢复。

为避免测试本身的压缩任务队列成为限制，测试服务保留一个 worker，并把有界任务容量和事件分发上限
从 4 调至 8；硬内存预算仍为 16 MiB。其余连接、帧和压缩参数沿用 dev.100/dev.101。

## 调度与所有权断言

- 六个成功 FIRST DATA 帧来自六个不同存活 Stream，均为 FIRST、非 LAST。
- 随后的 30 个续帧按这六个 Stream 的既定顺序轮转五轮；再次轮到同一流之前，其他五条均已发送一帧。
- RESET 候选无 DATA；六条压缩正文和 RAW 正文逐字节交付，发送消息数正确，TX 池及最终消息预算归零。

该测试证明固定六条存活流、单项 DATA TX 池场景下的 36 帧/六轮顺序，不构成任意流数、持续压力下的
最大等待时间、吞吐或跨机器 SLA。

## 验证结果

- GCC Release `test_transport/default` 连续 6/6 通过；每次检查 36 个帧记录并观察到 60 次池满重试。
- GCC Release 项目全量测试 91/91 通过，耗时 147.318 秒。
- clang-format 23.1.3 变更行检查和 `git diff --check` 通过。
- 临时将成功发送后的调度游标错误地停留在同一 Stream，六流回归按预期在 FIRST 帧轮转断言失败；
  恢复生产代码后六次定向测试和全量套件通过。

本次只扩展测试、文档和开发版本号，不改生产运行时、公开 API/ABI 或 wire。五条及以上流的长期公平
保证、消息延迟界、吞吐阈值、跨机器基线，以及完整预算/取消矩阵仍待验收；#241/#235 与 V2 整体验收
仍开放。

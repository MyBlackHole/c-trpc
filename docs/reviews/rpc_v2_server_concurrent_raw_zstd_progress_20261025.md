# 公开 Server 并发 RAW/Zstandard 进展回归

日期：2026-10-25。版本：`2.0.0-dev.84 -> 2.0.0-dev.85`。关联 #241、#235。

## 验收目标

在真实公开 Server 与双 DATA 连接上同时保持压缩消息来源和 RAW 消息来源活跃。服务端应用持有部分解压输出期间，验证另一物理 DATA 成员上的 RAW 源能持续补充有界在途窗口并交付；压缩源也必须完成固定批次。该回归用于证明并发来源下的有限进展，不定义长期公平性阈值。

## 场景与证据

- 真实公开 `tr_server`/`tr_client` 建立两条 DATA 物理连接和两个 transfer。Server 接收 Zstandard，单条解码正文上限为 1 MiB，压缩任务容量为 8。
- 第一成员连续提交 32 条真实 1 MiB Zstandard 消息。正文各自填充不同字节；服务端逐字节校验。前五条解码输出被应用接管并持续持有，之后 27 条在回调中释放，避免持有输出使预算自然拒绝并关闭压缩成员。
- 第二成员由独立测试线程持续发送 1 字节 RAW 消息，最多维持 32 条已接受、未交付消息；每次收到服务端完成回调后立即补发下一条。总消息有 16,384 条保护上限，若一次测试触及上限会使断言失败，防止发送循环脱离压缩批次继续运行。
- 服务端记录第一条与第 32 条 Zstandard 回调时已交付的 RAW 数量，并断言两者之间至少完成 32 条 RAW 消息。测试链接包装确认 Zstandard 与 RAW 消息的提交标志，并验证两类首条消息被路由到不同 DATA 物理连接；后续 RAW 消息保持在同一 DATA 连接代次。
- 压缩批次结束后，测试停止 RAW 生产线程并排空已接受消息，再逐字节复核五条仍被持有的 1 MiB 输出，随后释放并正常 drain/销毁 Server 与 Client。

## 观测结果

- GCC Release 的首次定向运行、五次复跑及完整 Release 套件中的定向运行，共七次均通过；压缩批次期间 RAW 交付数为 1,372–2,598 条。该数量随运行调度变化，测试只要求最小值 32，不将观测值当成性能阈值。
- GCC ASan/UBSan（`detect_leaks=1`）下定向测试通过，观测到并发区间内 4,514 条 RAW 消息。
- GCC TSan 下定向测试通过，观测到并发区间内 2,579 条 RAW 消息。
- GCC Release 完整测试套件 91/91 通过，耗时 141.520 秒。
- `git diff --check` 与系统 clang-format 23.1.3 的改动行复核通过；项目固定 clang-format 18.1.8 未执行。

## 结论边界

测试覆盖一个固定 32 条 Zstandard 批次，以及在该批次期间持续补充的有界 RAW 在途窗口。它能发现两来源并发时任一方完全不进展，但不测量每条消息的最大等待时间、单位时间吞吐或长时间饱和下的公平比例。完整 #241/#235 仍需明确持续负载时长、消息大小/配比、延迟阈值、稳定基线和更广预算/取消组合。本次只改集成测试、文档与版本，不改生产运行时、公开 API/ABI 或 wire。

# RPC-B3：有界业务执行、请求持有与背压回复

## 基线和实际范围

基于 #264 的 `3f8c35c0fdfce9a9a4c07cab20944cd1f9c67171`，树为
`b045a289f293a0b9fbe519e5e1101fd753ce91a5`。关联 #240、#243、#241、#248、#239。
本切片把已有方法路由、记录绑定和通用任务执行器组合成服务端业务派发适配，
不再在 Reactor 的方法回调内执行实际业务，也不新增一套线程池或语义状态机。

新增 `rpc_record_dispatch.h/.c` 和真实 TCP 测试；任务执行器只增加带锁的
完成所有者身份查询，用于拒绝绑定错误执行域，不导出槽位或私有布局。
Xmake 新增一个生产源和一个测试目标；旧网络入口、SDK名单、工作流、旧测试
和静态分析基线不变。旧 `tr_rpc_endpoint`/V1 默认入口仍未切换。

## 借鉴与执行边界

参考 [libuv 工作池](https://docs.libuv.org/en/v1.x/threadpool.html) 将工作与
所有者完成分开，但复用 c-trpc 已有有界 task_executor，不采用全局隐式池。
[gRPC 取消说明](https://grpc.io/docs/guides/cancellation/) 区分取消通知和业务
协作停止；本实现同样不能强制中断任意业务函数，不因取消成功就提前释放参数。

派发器借用由同一个 Reactor 所有者交付完成的执行器。外层必须持续调用执行器
的 dispatch，然后调用派发器 pump，并在可写、资源解除和完成通知后继续推进。
新模块不注册自动事件源。真实集成测试用一个已有 Reactor 定时器每毫秒驱动
上述步骤；这是测试宿主的驱动器，不是已经迁移到默认 Endpoint 的生产调度方案。

## 请求、任务与响应的所有权

路由回调取得的记录字节只活到返回；本适配在预算预约成功后复制元数据与业务体，
形成独立任务快照，工作线程不读取已经释放或被重用的 Channel 接收缓冲。
当前是一次有界复制，不声称异步接收零复制。方法参数仍由调用方保持到整个
派发器销毁；不同调用可以并发使用相同参数，业务方负责参数自身同步。

每调用有数量上限的 FIFO，涵盖排队、已投递以及已完成待发送三类事件，同时受
共享字节预算限制。一次只向执行器投递该调用的一个事件，上一事件的回复全部被
传输接受后才投递下一事件。不同调用独立轮转推进。执行器满载保留已经持有的输入，
不重放业务，不丢弃已吸收字节；本调用接收队列超限则本地 RESOURCE_EXHAUSTED。

工作函数只取得数值调用身份、只读请求、取消令牌和不透明 reply，不取得可变
路由/Stream对象。每个事件可追加有限条响应，受方法单消息大小、单事件总字节与
条数限制。先预约包装和载荷再分配/复制；零长度仍是一条。追加失败锁存错误，
即使业务忽略错误并返回 OK，也不能交付被截断的成功批次。非OK返回或最终错误
丢弃当前事件的未发送正文，之前事件已发出的内容不可撤销。

HALF_CLOSE 默认结束响应；业务也可显式选择最终状态。所有回复继续经过原绑定
的基数和顺序检查，缺少 ONE 响应不能假报成功。当前不支持工作函数返回后继续
生产响应，也不提供自定义初始/尾部响应元数据，不能冒称完整流式应用 API 已交付。

## 发送不是重新执行业务

每轮每调用最多投递一个任务或发送一条记录。初始元数据、正文和 FINAL_STATUS
分别通过真实路由绑定发送。AGAIN 保留精确回复和发送阶段，只重试发送，不重新
运行 handler，也不提前选择发送成功终局。下一回复链指针在发送接受之前保存，
接受之后不读取可能已经被底层释放的载荷。独立 TX 正文/前缀可能长于派发器存活，
预算域必须继续有效。

本地 terminal 的 final_accepted 只表示 FINAL 已被传输接受，不表示已写出或
远端已收到。正常业务结果/错误可以产生真实最终记录；未知方法、畸形输入、
接收资源拒绝及本地取消仍可能只是本地终局，尚未补齐自动拒绝 FINAL/RESET。
本适配不自动 close Stream，避免未经证明的关闭顺序截断已排队数据。

## 取消、延迟通知与停止域

路由选择终局后立即取消在途任务，释放未提交或已经完成的事件，但 submitted
对象直到执行器 done 才能释放。用户 terminal 延后到该调用全部任务已静默并清理，
至多一次；槽位仍需外部移除路由后显式退役，不能仅收到终局就复用弱能力。

正常 destroy 停止准入、本地取消，存在在途工作返回 AGAIN，外层继续交付借用
执行器的完成再重试。派发器不擅自停止可能被其他模块共享的执行器。

父 Reactor 已 join 后，先调用 reap_stopped 取得恢复租约、进入清理域并取消；
若存在 submitted 返回 AGAIN。外层统一 stop/join/adopt_cleanup/dispatch 执行器，
再重试 reap。不得先在错误线程调用 done，再追认授权。剩余路由复用原恢复机制。
若旧 owner 已选本地取消但工作一直未退出，延后到清理线程的通知必须变成
OWNER_STOPPED/CANCELLED，不能沿用 ON_OWNER 标记。第一轮本地测试暴露并修正了
新实现中的这一交付域问题，然后重新执行最终验证；不包装为旧生产缺陷。

## 实际测试与本地证据

`test_rpc_record_dispatch` 使用真实本机 TCP、两个 Reactor、Channel、方法路由、
调用绑定和通用执行器，不使用事件循环替身。服务端把接收缓冲立即改写并释放，
固定工作线程在随后执行，验证请求有独立存储；同调用活动计数验证不并行执行。

覆盖四种基数、空消息/零消息流、有界多响应、4096字节业务；慢调用不阻挡另一
调用完成；共享执行器被其他任务占满后 RPC 输入仍保留并恢复。分别在初始元数据、
正文和最终状态处连续拒绝发送，验证同一载荷重试、handler只执行一次；另用真实
128字节窗口和接收信用返还触发背压。错误返回、忽略追加超限/分配失败、ONE缺失
响应均不假成功。七个构造分配点逐一失败，预算恢复；错误执行器 owner 绑定被拒绝。

取消测试故意让业务忽略令牌、生成迟到结果，确认结果被清理且终局延后到工作退出。
分别验证原 owner 收敛、本地先取消再父停止，以及父停止先于取消的清理域流程。
没有强制中断业务、没有把测试宿主正常停止扩展成所有致命退出组合的证明。

## 后续与限制

本轮是可用的库内服务端业务派发适配，旧Endpoint/Client/Server仍未创建它；
下一切片必须整合生产端点的流路由、完成/可写驱动与自动错误终止，替代后删除
旧路径，不长期维护平行端点。未实现期限/慢OPEN定时、认证、网络压缩与方向
协商、流控重设计、连接组DATA、TLS或性能验收。计费不包括任意业务自行分配的
内存、线程栈、内核资源或整个RSS。整体任务仍保持开放。

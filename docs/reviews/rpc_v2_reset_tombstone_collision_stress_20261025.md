# RPC V2 RESET 墓碑索引碰撞压力回归

日期：2026-10-25。关联 #242/ERR-E。版本：`2.0.0-dev.64 -> 2.0.0-dev.65`。

## 覆盖范围

本切片只扩展 `test_reset_tombstone_index`，不改墓碑索引实现、公开 API/ABI 或线协议。测试使用内部 home 计算 helper，挑选 512 个不同流 ID，使其在 512 槽表上都映射到同一 bucket；表同时驻留 256 个键，填充率为 50%。这构造了可复现的最坏线性探测簇，不依赖计时或随机种子。

初始填充断言第 i 个插入恰好探测 i+1 个槽。随后连续执行 256 轮 FIFO 淘汰与同一墓碑环槽复用：每轮都移除当前簇首、确认旧键不可查、更新环槽并插入一个新碰撞键。插入应探测 256 个槽；周转结束后，256 个驻留键均返回预期环槽，256 个淘汰键均为 stale。

## 验证

- GCC Release、TSan、ASan/UBSan 下 `test_reset_tombstone_index` 均为 1/1 通过。
- 临时令大于 8 槽的表跳过 backward-shift 修复时，新测试在替换插入的探测次数断言失败；恢复实现后同一目标通过。
- `git diff --check` 在提交前执行。

## 边界、风险与回滚

该测试验证 256 路合成碰撞、删除簇修复和重复环槽复用的正确性，明确展示开放寻址最坏探测随簇长度线性增长；它不测耗时，不覆盖 `max_streams=40000` 下的全尺寸对抗输入，也不证明实际远端调用方能够稳定操控当前复合哈希的所有输入位。最大容量的 CPU 成本仍待独立压力评估。

回滚可撤销 dev.65 提交：将 `xmake.lua` 和 README 版本恢复至 dev.64，移除此测试与记录，恢复剩余工作台账描述；随后在 Release 下重跑 `test_reset_tombstone_index`。

## 验收标准

1. 256 个不同流 ID 在容量 512 的索引中拥有同一 home bucket。
2. 插入、碰撞查找、FIFO 删除和环槽复用保持精确键/槽关系，所有淘汰键不可查。
3. Release、TSan、ASan/UBSan 下单元目标通过，且生产实现不变。

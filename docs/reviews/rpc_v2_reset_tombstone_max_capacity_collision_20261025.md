# RPC V2 RESET 墓碑索引最大容量碰撞周转

日期：2026-10-25。关联 #242/ERR-E。版本：`2.0.0-dev.66 -> 2.0.0-dev.67`。

## 覆盖范围

本切片只扩展 `test_reset_tombstone_index`，不改墓碑索引实现、公开 API/ABI 或线协议。测试使用生产最大配置
`max_streams=40000` 和容量 131072 的索引，填满全部历史槽。先用共享 home 计算 helper 找出 512 个互不相同、映射到同一
home bucket 的流 ID，再插入 256 个碰撞键，随后填入其余 39,744 个不同键。

测试连续 256 轮淘汰当前碰撞簇首并复用对应历史槽。每轮在删除后、复用前确认下一驻留碰撞键仍能查回原槽，并确认旧键
已不可查；周转后再核对未复用的 39,744 个键、全部驻留碰撞键和淘汰键。该顺序直接检查大表删除的 backward-shift 修复，
避免新键恰好填补空槽而掩盖幸存键失联。

测试将插入、查找和 `remove` 自身报告的探测数合计限制在 `64 * max_streams`，即 2.56m。`remove` 的探测输出只计删除前
定位键的查找，不计 backward-shift 扫描的槽访问；该数值不是耗时或 CPU 成本上界。

## 验证

- GCC Release、TSan、ASan/UBSan 下 `test_reset_tombstone_index` 均通过。
- 临时让大于 8 槽的索引跳过 backward-shift 修复，并只运行本测试时，新断言在删除后、复用前查找幸存键处失败；恢复生产实现后通过。
- `git diff --check` 在提交前执行。

## 边界、风险与回滚

该回归覆盖最大配置表尺寸、满历史占用和 256 路同 home 碰撞簇交错，不覆盖 40,000 个键全部同 home 的极端情况；该输入仅
初始插入就需要约 800m 次线性探测，故没有把它作为常规单元测试。它也不测真实 Channel/网络上的 40k 并发压力或机器耗时。

回滚可撤销 dev.67 提交：将 `xmake.lua` 和 README 版本恢复到 dev.66，移除新测试、记录并恢复剩余工作台账；随后在 GCC Release 下
重跑 `test_reset_tombstone_index`。

## 验收标准

1. 最大配置表填满 40k 历史槽，并保留 256 个确定性同 home 碰撞键。
2. FIFO 删除后、环槽复用前，剩余碰撞键仍可查；周转后其他历史键和新驻留键映射正确，所有旧碰撞键不可查。
3. Release、TSan、ASan/UBSan 下目标通过，且跳过大表簇修复的变异被测试捕获。

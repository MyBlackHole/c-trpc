# c-trpc 压缩与 TLS 安全传输需求

**状态：持续有效的安全与验收要求。TLS 与可选 Message 压缩已接入当前开发分支；本文件不代表完整发布验收或稳定协议承诺。**

本要求面向通用 RPC/传输，不引入备份、存储、持久化、提交或业务密钥语义。
当前开发分支提供明文 TCP 和可选 TLS 1.3 字节端点，以及可协商、逐消息选择的
Zstandard Message 变换。默认仍使用明文 TCP 和 NONE。CRC32C 只能检测损坏，
**不能提供认证、机密性或防止主动篡改**；不可因本文件新增而对外宣传支持。

## 一、优先级与阶段

| 阶段 | 状态 | 目标 |
| --- | --- | --- |
| S0（当前） | 已实现 | 现有明文 TCP 行为、分片、流控、资源上限和 SDK 保持不变 |
| S1（P0） | 已实现，验收未完成 | TLS 1.3 传输保护、服务端身份校验、关闭与失败语义 |
| S2（P0） | 已实现，平台验收未完成 | 多分片、连接组 CONTROL/DATA、轮换与排空的 TLS 生命周期闭环 |
| C1（P1） | 已实现，发布验收未完成 | 默认关闭的无字典 Zstandard Message 压缩、显式协商与有界资源 |
| C2（P1） | 部分完成 | 本机 RPC 与连接组 TLS/压缩矩阵、侧信道审查；长期可靠性、真实业务负载与发布阈值仍待验收 |

TLS 与消息压缩已有实现基线，安全部署和发布验收仍按阶段单独推进。
安全需求未满足前，不将 c-trpc 直接暴露到不可信公网。
各阶段必须分别记录设计决策、实现与验收证据；功能、基准、验收证据不可互相冒用。

## 二、层次与不变量

```text
应用/业务数据 ──> 可选 RPC 编码 ──> Message 独立消息层
                                     ├─ 逐消息 none / Zstandard 变换
                                     └─ 长度、工作区与缓冲所有权
                                                |
                                 Channel / Stream（传输层）
                                 ├─ 方向性能力与消息准入
                                 ├─ TRP1 分片/控制帧与网络流控
                                 └─ 接收有界重组后交 Message 解码
                                                |
                                         Reactor 连接 I/O
                                                |
                                 明文 或 TLS（保护完整连接字节流）
                                                |
                                               TCP
```

**发送顺序**：RPC 编码（如存在）→ Message 层可选变换 → Channel/Stream
逻辑消息准入及 TRP1 DATA 分片/封帧 → TLS（如启用）→ TCP。

**接收顺序**：TCP → TLS（如启用）→ TRP1 验帧/有界重组 →
Message 层按方向能力和逐消息策略解压并校验原始消息长度 → Stream/RPC 上层回调。

**模块归属**：压缩算法、完整消息变换、长度校验、缓冲所有权与工作区限制属于
独立 Message 层 `src/message/`，不是 RPC 编解码器、Channel 的算法实现或 Reactor
字节收发。Channel/Stream 负责方向性能力协商、逐消息准入、DATA 分片/重组、网络
信用与终止；RPC 只提供业务体是否获准压缩的策略；普通 Stream、RPC 业务消息体和
连接组 DATA 复用同一 Message 能力。TRR1 路由前导、RPC/Channel 控制信息、身份和
凭证元数据不得压缩。详细协议与流控决策见 [ADR-008](decisions/ADR-008-message-compression-protocol.md)。

- **两种独立能力**：Message 层压缩只作用于明确允许的完整逻辑数据消息；
  TLS 属于连接 I/O 适配，保护具体 TCP 连接的完整字节流。
  不允许把 TCP/TLS 记录当作分帧或 RPC 消息边界。
- TLS 握手成功并完成身份校验后，服务端才能读取 TRR1 路由前导、
  TRP1 HELLO 或应用 RPC；客户端才能发布相应连接就绪/数据准入。
  TLS 配置为必需时，握手失败或收到明文都必须直接拒绝，
  **禁止自动降级到明文**。现有默认明文行为为兼容模式，不代表安全默认。
- Message 层先压缩获准的逻辑数据消息，Channel 封帧后由 TLS 加密；
  **禁止 TLS 记录层压缩**。
  TLS 1.3 的遗留压缩字段只能选择空压缩；不能将它视为应用压缩协商。
- 每个 Reactor 继续作为连接和 Stream 可变协议状态的唯一所有者。
  工作线程可承担昂贵压缩、证书材料预处理等工作，但结果必须通过
  已有有界完成队列回到原所有者，不增加无理由的跨层线程或无界缓冲。

## 三、TLS 传输要求（P0）

### 3.1 认证与密码策略

1. 首版强制支持 TLS 1.3；若未来因兼容需要允许 TLS 1.2，
   必须由应用显式开启、单独验证，只允许现代 AEAD/前向安全套件。
   禁止 SSLv2/v3、TLS 1.0/1.1、空加密、弱加密以及不安全回退。
2. 客户端必须验证可信证书链、有效期、扩展密钥用途与服务端
   主机名/IP（证书 SAN）；验证失败默认拒绝，不提供隐式
   “忽略证书错误”选项。服务器必须支持配置自己的证书与私钥。
3. 支持配置可信 CA；提供可选及强制的双向证书认证（mTLS）。
   如果启用连接组，CONTROL 与 DATA 连接必须重新认证，
   并验证同一组要求的安全身份绑定与现有 `epoch`/成员代次，
   **不得只相信远端提供的 TRR1 标识**。
4. 明确区分 `disabled` 与 `required` 语义；不能为了让旧应用继续连接
   在 `required` 失败时偷偷走明文。未来未实现的 TLS 模式必须明确报
   `TR_ERR_UNSUPPORTED`（或有文档的等价状态），绝不伪装成功。
5. 默认禁止 TLS 1.3 早期数据（0-RTT），避免 RPC 非幂等请求重放；
   不导出未受保护的密钥材料，不在普通日志输出私钥、令牌或完整载荷。
6. 证书轮换必须保持已有连接与新连接的材料所有权独立，
   更换失败保留上一份有效配置或明确失败关闭，不能释放仍被握手引用的上下文。
   未来如采用 ALPN，明确约定协议标识、缺失/错误标识的拒绝语义并版本化。

### 3.2 事件驱动与资源所有权

1. TLS 会话/握手状态由**连接所属 Reactor 所有者**修改。
   采用非阻塞握手/加解密；`WANT_READ/WANT_WRITE` 与 epoll LT
   关注事件精确对应，不忙等、不增加每连接工作线程。
2. TLS 初始化、握手、认证、读写、关闭与重连共用有界资源和
   `CLOCK_MONOTONIC` 绝对总期限；不能每次可读/可写事件重置握手期限。
   TLS 尚未就绪的连接仍占容量/内存预算，并在到期后被回收。
3. TLS 写入可能消耗部分明文、产生尚未完全写出的密文。
   必须定义调用返回时的所有权与重试语义，不得用裸
   `sendmsg(iovec)` 的现有零复制声明代表 TLS 模式。
   TLS 缓冲、记录与 pending 写状态均须在内存预算中记账；
   `TR_AGAIN` 等背压不得提前归还已移交的数据。
4. 半关闭、对端 `close_notify`、不干净关闭、应用排空和强制销毁必须区分。
   优雅关闭可以尝试有界发送 `close_notify`，但销毁不能无期限
   等待对端，且只有跨过所有者回调静默屏障才能释放 TLS 会话/回调参数。
5. 自动重连须重新握手并重新认证；不得复用旧连接 TLS 对象、
   旧流代次或将未确认执行的 RPC 自动安全重放。
   多 Reactor/多分片以及共享/拆分连接均有各自独立 TLS 会话。
6. 加密状态不可泄漏到公开 SDK 的内部指针、fd、槽位或库特定结构布局。
   需要配置时优先提供高层语义选项，不把加密库内部对象固定为稳定 ABI。
   后续引入 kTLS 必须另行验证内核/密码套件支持与性能，不能预先承诺零复制。

### 3.3 交付验收

- 信任链正确与不可信 CA、证书过期/主机名不符、证书用途不符、
  mTLS 缺证书/身份不符、协议版本不匹配与明文降级攻击。
- 握手任意 TCP 分片、`EINTR/EAGAIN`、双向读写兴趣切换、
  证书轮换失败、分配失败、关闭/取消/超时/重连/重复销毁。
- CONTROL/DATA 身份绑定、TRR1/TLS 先后顺序、多分片监听、
  含既有应用载荷的断连、优雅排空与错误恢复。
- GCC/Clang、ASan/UBSan、TSan 与精确静态分析门禁；
  真实跨进程互通，标准 TLS 实现互通测试与长期负载。
  逐项证明事件源已解绑、fd/密钥/缓冲所有权已归还。
- 记录握手成功/失败类型、协商版本、连接准入拒绝和性能成本；
  不输出证书私钥或应用敏感数据。
  未覆盖的场景不能当作“TLS 已达到生产级安全”发布。

## 四、消息压缩要求（P1）

### 4.0 模块归属与复用要求

- **唯一实现归 Message 层**：在 `src/message/` 实现通用、可关闭的逻辑消息压缩/解压；
  Channel/Stream 消费该能力，不包含第二份压缩编解码器。RPC 端不得再实现第二套
  压缩器，也不得要求业务自行压缩后再调用传输接口。该归属由 ADR-008 确定。
- RPC 仅负责产生逻辑消息并携带“是否允许压缩”的应用策略；
  未使用 RPC 的 Stream 数据以及连接组 DATA 也能复用同一实现。
  压缩策略可以按消息、方法或数据类别约束，但必须经过双方协商、
  敏感数据禁压缩检查与传输层资源准入，不能由 RPC 强制打开压缩。
- **不进入字节流层**：不在 `recv()`/`sendmsg()`、TLS 记录、
  每个 TRP1 帧或 TCP 字节段上独立压缩。压缩边界固定为
  单条完整逻辑消息，发送在 DATA 分片之前，接收在 DATA 重组之后。
  CRC/帧格式、连接组 TRR1 路由前导和 CONTROL 控制消息保持原职责。
- 默认 `none` 路径应复用现有缓冲与分散/聚集发送，不增加新的
  消息复制、分配、工作队列或跨线程跳转；压缩开启时的额外内存、
  CPU 和可能失去的零复制收益必须明确计量与验收。

### 4.1 默认、粒度与协商

1. **默认不压缩**。应用显式选择可压缩业务数据类型/通道；
   认证信息、访问令牌、密钥、会话标识、授权元数据和
   混合攻击者可控文本与秘密的内容，默认禁止压缩，
   即使已经通过 TLS 加密也不能自动豁免。
2. 首个候选编码为 Zstandard（RFC 8878）的独立消息帧；
   首版允许 `none` 与一个明确版本的受支持算法。
   采用何种线协议扩展、算法标识、内容原始长度和字典标识，
   必须另立 ADR，明确混部兼容/升级/降级/拒绝规则；
   **本需求文档不预占 TRP1 标志位或 SDK 结构体字段**。
3. 仅在双方已完成当前的通道能力协商并确认一致算法后才能发送
   压缩消息；未知算法、非法标志和未协商压缩都要拒绝，
   绝不能把压缩字节当原始应用字节上交。
   旧对端不支持时，仅按显式配置允许回退到 `none`，
   不改变旧线协议默认行为。
4. Message 层对**完整逻辑消息体**执行压缩，Channel 完成压缩后的 DATA 分片；
   接收端完成验帧和有界重组后，由同一 Message 层解压，RPC/Stream 上层回调只看到
   原始逻辑数据。
   流式 RPC 每个独立消息都具有自己的压缩边界，不跨消息或
   连接复用可能混淆身份/秘密的隐式字典状态。
5. 首版不启用远端提供的自定义字典；若将来支持，
   必须对字典标识、来源信任、容量、版本/代次和销毁所有权单独建模。

### 4.2 资源安全与背压

1. 压缩输入、压缩结果、解压后的**声明长度与实际输出长度**、
   解码窗口、字典、临时工作内存、消息数量和并发任务都必须有上限。
   旧有 `max_message_bytes` 对应用**原始逻辑消息长度**继续生效；
   压缩后的网络体积也必须满足独立的线协议/资源上限。
2. 未知原始大小、不可信头部、超大窗口、超大膨胀倍率或分配失败
   不能先分配巨大内存再报错；必须在解压过程中累计检查
   实际输出、窗口和工作预算，拒绝压缩炸弹与 CPU 耗尽。
   仅限制“压缩比”**不能替代**绝对输出上限和时间/资源预算。
3. 逻辑流量控制与内存准入必须能同时约束网络字节和未压缩消息占用，
   不能借“压缩后更小”绕过原有 Stream/分片/全局语义额度。
   对既有网络字节额度与新增的解压内存准入分别记账，
   原始消息大小在解压前检查，最终载荷归还时归还匹配的额度；
   具体信用消耗与回补点由 ADR 定义并进行断连/取消验证。
   若任一侧预算不足，按既有 `TR_AGAIN` / 失败所有权契约拒绝，
   不创建第二个无界发送队列。
4. 明确压缩资源所有权转移点：编码失败、解码失败、中途取消、
   截止时间到期、连接关闭、重新接入、并发停止时必须一次性释放。
   原始/压缩/解压缓冲不得重复释放或在工作线程中被 Reactor 提前回收。
5. 若压缩有明显 CPU 成本，应使用受限工作任务回到原 Reactor，
   不能在 Reactor 所有者的 I/O 处理轮次上执行无上限压缩。
   禁止未经实验就宣称加密模式仍保留现有 `sendmsg` 零复制收益。

### 4.3 性能与安全验收

- 双端算法/能力不一致、旧对端、压缩无收益、不可压缩随机字节、
  0 字节/小消息、多片大消息、TCP 任意分片与重连/取消。
  还需验证直接 Stream、普通/流式 RPC、连接组 DATA 对同一
  传输层编解码实现的复用及默认 `none` 路径零额外复制。
- 恶意头部、未知原始大小、伪造长度、截断/损坏、
  巨大解码窗口、压缩炸弹、资源池耗尽/逐分配失败与压缩错误回滚。
- 在 TLS 开/关及连接组、多分片、批量/控制混合负载下证明
  机密数据不会因默认压缩而混入攻击者可控制的压缩上下文。
  对压缩侧信道风险进行专门安全审查，不能只以 TLS 认证成功结案。
- 对相同负载比较 `none` 与压缩 ON 的吞吐、P50/P99、CPU、
  额外分配/复制、最大 RSS、拒绝率、压缩率和端到端完成率。
  关闭负载与开环负载分开，报告置信区间/重复样本和性能回退；
  结果不稳定时默认 OFF，不能仅用吞吐局部改善推广。
- 生产实现还需 ASan/UBSan/TSan、静态分析与正反故障注入通过，
  才允许将该能力从实验状态提升至生产配置。

## 五、先决条件和完成定义

- 首版 TLS 和压缩实现**不得**同时修改既有 TRP1 帧字段/公开 SDK
  而没有独立线协议/接口兼容性决策；必须有升级和回滚测试。
- 独立 PR 建议顺序：TLS 接入点/状态机 ADR → 非阻塞 TLS
  单连接与认证 → 生命周期/连接组绑定 → 压缩协议/资源 ADR →
  可选 Zstandard → 组合安全与性能验收。
- 需求完成只表示**设计与验收边界已经约定**，不得在 README
  标注“支持 TLS/压缩”或关闭安全发行阻塞项。
  当前仅验收文档追踪；实现完成、CI 通过、可在不可信网络部署
  必须分别有真实证据，且 #154 仍需其他工程条件独立闭环。

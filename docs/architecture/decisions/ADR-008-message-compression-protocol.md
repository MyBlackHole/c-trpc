# ADR-008：独立 Message 层压缩与有界网络推进

**状态：提议中**
**日期：2026-10-24**

## 背景

`src/message/` 已有拥有型消息、Zstandard 有界变换和有界异步服务；V2 的
Channel、普通 Stream、RPC 业务体和连接组 DATA 尚未形成共用的网络压缩路径。
Issue #235 规定压缩归独立 Message 层，Issue #241 要求将网络信用与消息存储
分账，并证明压缩后编码长度 `C` 大于网络窗口 `W` 时仍能持续推进。

现有 Channel 将一条完整消息与窗口比较；接收侧在应用释放消息后才回补窗口信用。
直接把压缩后的完整消息交给该路径，会将 `C > W` 永久拒绝，也会把压缩缓冲
和网络在途信用错误地视为同一资源。

## 决策

1. **变换归 Message 层。** `src/message/` 负责完整逻辑消息的 `none`/Zstandard
   变换、实际输入/输出长度检查、窗口和工作区限制、缓冲所有权。Channel/Stream
   只负责能力协商、逐消息准入、分片、重组、网络信用与终止。RPC 只能为业务体
   提供压缩授权；连接组 DATA 复用同一 Message 能力。控制、路由和身份元数据不压缩。
2. **压缩默认关闭且逐消息选择。** `none` 沿现有路径发送，不创建变换任务、不复制
   载荷、不引入新的线程跳转。调用方显式选择 Zstandard，并承担敏感业务体禁压缩
   的策略责任；不使用远端字典。无收益时是否回退 `none` 必须由调用方显式选择。
3. **用已协商 feature 门控方向性能力帧。** 新增一个 Channel feature bit 表示
   双方理解 Message 能力扩展；只有 HELLO/ACK feature 交集含该 bit 时才交换
   `MESSAGE_CAPS`。该帧声明本端可接收的算法集合和最大编码网络负载。发送算法
   依据对端接收能力选择，接收算法依据本地策略限制。没有共同 feature 的旧对端
   不会收到新帧或压缩 DATA，继续使用 `none`。
4. **压缩 DATA 使用逐消息前缀。** 协商完成后，DATA 可带 `COMPRESSED` 标志。
   仅 FIRST 帧前缀携带信封版本、算法 ID、编码体长度、解码长度和零保留字段；
   所有 DATA 负载仍受帧上限和网络信用约束。保留现有 TRP 固定帧头及其零保留
   字段语义，不在帧头中偷用未版本化字段。
5. **网络信用按实际 DATA 负载计算。** `C` 表示压缩算法输出，网络信用按
   `C + 信封长度` 消耗。发送端可分帧发送并按对端 WINDOW_UPDATE 继续推进；每轮
   向一个流发送有限帧并轮转，控制帧仍使用现有有界优先级规则。
6. **接收侧先预约再接收。** 接受压缩消息 FIRST 前，必须取得有界编码重组存储，
   验证声明的 `C`、`U`、算法和本地上限。每个分片复制进已预约存储后即可归还
   对应网络信用；这笔信用不代表存储已释放。完整编码体交给 MessageService 后，
   解码输出 `U`、编码体、工作区、应用保留和任务槽分别计入各自硬上限。
7. **资源拒绝具有终局语义。** 算法未协商、长度/窗口越限、前缀错误、存储预约
   失败或流序失效都必须显式拒绝/终结该消息或流，不能以永远 `TR_AGAIN` 假装
   可恢复。异步变换接受前预留有界完成责任；取消、连接代次变化和迟到结果只在
   原所有者裁决，过期结果不得发送或交付。
8. **分入口交付。** 第一实施切片建立 Channel 方向性能力协商；后续先闭合
   Channel/Stream 消息变换及 `C > W` 活性，再分别接入 RPC 业务体和连接组 DATA。
   不能以通用 Stream 的通过代替其余两个入口的验收。

## 影响

- Channel feature、消息能力控制帧和 DATA 压缩标志构成可选扩展；压缩没有协商
  时维持现有字节语义。
- 当前能力帧实现只接受本地空算法通告；`message_caps_ready` 表示能力控制帧交换
  完成，不表示 Channel 已能收发压缩 DATA。非零本地接收算法会在数据路径完成前
  返回 `TR_ERR_UNSUPPORTED`。
- 本地配置需要区分解码消息上限、编码网络负载上限、解码工作区和任务并发。
- 接收缓存池容量是网络信用背后的硬存储上限；解码后应用持有的消息由 Message
  存储预算另行约束。
- 需要修改当前“完整消息必须一次占满窗口”的 DATA 发送准入，增加按帧信用推进
  与公平轮转。不得只扩大默认窗口来消除 `C > W`。
- TLS 仍在 Message 变换和 Channel 封帧之外；压缩在 TLS 保护之前执行。启用 TLS
  不改变默认关闭与敏感数据禁压缩规则。

## 拒绝的方案

- 在 RPC、Channel 算法实现和 Reactor 字节收发各自放置压缩器：造成三套缓冲、
  资源和安全策略。
- 压缩每帧、TCP 段或 TLS 记录：破坏完整消息边界或把 TLS 记录误作应用协议。
- 让接收端直到应用释放 `U` 才回补 `C` 信用：令 `C > W` 无法推进，并混淆编码
  网络信用与解码存储信用。
- 用扩大的窗口或无限待发队列解决大消息：不构成全局内存上限或公平性证明。

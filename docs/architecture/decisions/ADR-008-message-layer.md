# ADR-008：独立消息层与传输层边界

**状态：提议，待实现。** 本文记录架构选择，不表示 Message 压缩功能已交付。

## 决策

在 `src/message/` 建立独立、通用的逻辑消息层：
- 消息层：完整消息边界、原始/编码长度校验、压缩/解压、缓冲区变换及资源所有权；
- 传输层 Channel/Stream：算法能力协商、策略准入、TRP1 分片/重组、流量控制、连接组、取消与终止；
- RPC 层：可选序列化、方法语义与敏感消息禁压缩策略；
- Reactor：单所有者 I/O 事件和有界 TX/RX 资源；TLS 是连接 I/O 适配，不是消息压缩。

发送：RPC/应用 → Message → Channel/Stream → TLS（可选）→ TCP。
接收：TCP → TLS（可选）→ Channel/Stream → Message → RPC/应用。

## 不变量

1. 未启用压缩时，Message 直接借用/透传现有消息缓冲，不引入新的复制、分配、队列、线程切换。
2. 每条完整逻辑消息独立压缩；发送在分片前、接收在重组后；不压缩 TRR1、控制帧、TLS 记录或 TCP 字节流。
3. 仅在下游成功准入时转移消息所有权；拒绝/背压时调用方保留所有权。取消、错误、超时、连接代次失效和停机时必须恰好释放一次。
4. 同时限制原始消息大小、压缩后字节、解压实际输出、工作内存、解码窗口、并发任务与 CPU 预算；传输网络信用与消息内存信用分别定义和回补。
5. 线程上的压缩任务只持有不可变快照和明确资源引用，完成事件回到原 Reactor 所有者后才修改 Channel/Stream 状态。
6. 算法协商与线协议标识必须单独 ADR 版本化；本 ADR 不预占 TRP1 标志位、不冻结公开 SDK/ABI，也不默认启用压缩。
7. RPC、普通 Stream 和连接组 DATA 共享同一消息层实现，RPC 不另建压缩算法路径。

## 先实施什么

先实现与协议无关的 Message 缓冲和压缩抽象（`none` 路径、上限验证、故障注入），再评估 Zstandard 后端；随后完成协商 ADR 和 Channel/Stream 接入。所有阶段需精确 CI、消毒器、资源泄漏、压缩炸弹与默认路径性能验收。TLS 按 #234 独立推进。

**未决问题：** Message API 是否持有 `tr_buffer`、如何避免发送路径额外复制、编码长度元数据和流控信用的确切记账时点，必须通过源码级接口设计和故障矩阵确认，不能仅凭此文档宣称完成。

# 自定义消息与 schema 演进设计：开源对照后的修订

日期：2026-10-29。状态：设计修订与候选对照阶段，生产实现未获批准、尚未开始。
用户选择自定义传输和业务格式，要求兼容演进，并要求学习开源项目的优点。
关联 #245、#241、#242、#247；主会话内联执行，不使用子 agent。

## 依据与撤回项

[开源对照记录](../../reviews/custom_message_open_source_lessons_20261029.md)逐项列出
Protobuf、FlatBuffers、Cap’n Proto、Thrift、SBE、Nanopb 的官方文档/源码、借鉴点、
不照搬的部分及验证要求。本文的项目决策来自该对照，不宣称第三方为本项目担保。

前两版 fbd9301/f670b77 只存在于设计文档，未部署。精确指纹拒绝、68 字节逐消息
完整描述头、固定 12 字节字段头以及“任何限额/压缩调整都换方法 ID”的规则撤回。
这些 wire 数字和规则不是兼容包袱，不以已有草案为由固化。

业务消息仍由自定义 TRP/RPC Record 承载，RAW 保留；不引入 Protobuf 运行库。
先交付可独立验证的 schema/codec 生成基础，再接入 OPEN 方法契约、四种基数的
Client/Server 桩和 Rust 安全 Call 包装。纯 codec 通过不能关闭 #245。

## 1. 把兼容性拆成四类

| 类别 | 检查什么 | 不意味着什么 |
|---|---|---|
| wire | 字段身份、表示、容器结构、新旧数据能否按规则读取 | 不保证接收额度足够或业务接受 |
| 生成 API | C/Rust 名称、类型、presence、借用与释放 | 源码 API 改名不必改变网络编号 |
| 业务语义 | 必要字段、默认含义、枚举处理、幂等依据 | 可跳过一个字段不代表业务能忽略它 |
| 运行策略 | 消息/工作限额、存储策略、压缩、lane、deadline、尝试策略 | 调整限额不自动等于 wire 类型破坏 |

兼容检查分别报告，不能只返回一个未解释的“兼容=true”。同 ID 的 wire 类型或
业务含义改变仍是破坏性变更；标量恰好能转换也不自动允许截断/重解释。

## 2. schema 与演进规则

采用受限单源 schema 和确定性中间描述，生成 C11/Rust 编解码器及方法描述。
构建输入可使用 JSON，网络不发送 JSON。输入重复键、未知键、非法标识符、引用
缺失/环、生成名称冲突、过深或过大定义在生成前拒绝；不动态下载远端 schema。

- family/type/service/method/field 的身份由源文件显式给出，不从文件名、注册顺序
  或内存布局推断。字段编号不复用；改名保留编号，源码顺序不改变 wire。
- 废弃字段先停止写入并标注 deprecated，历史编号和含义保留在描述/基线中；
  最终移除定义时 reserved 编号和名称，不能通过移除一版后再次使用绕过检查。
- 生成 API 显式表达缺席。C 用 has_value，Rust 用 Option；缺席、零、空内容不
  混为同一状态。初版不在 wire 解码器中引入普遍的 required 字段锁定。
- 业务必需项由方法验证规则处理。新增必需业务含义或改变既有含义属于语义变更，
  不能标为 optional 来假装兼容；通过新方法契约或明确的已协商特性并行升级。
- 新 optional 字段和可跳过的未知字段支持旧/新双向读取。解码成功不等于业务
  已经处理未知字段，不授予其权限，也不把它转成默认成功。
- 枚举默认保留未知数值及显式 Unknown 表示，不把新值变成 0。枚举数值可包含 0，
  不把类型/字段的正编号规则错误套在枚举值上；业务是否接受未知值单独验证。
- 新类型/新方法可以并行存在，破坏性语义不重用旧身份。现有 RPC 表的 service/
  method 唯一性继续有效，不以新 family 为由允许同一监听器错误派发重复 ID。

参考依据：[Protobuf 演进](https://protobuf.dev/programming-guides/proto3/)、
[显式 presence](https://protobuf.dev/programming-guides/field_presence/)、
[FlatBuffers 演进](https://flatbuffers.dev/evolution/)、
[Thrift requiredness](https://thrift.apache.org/docs/idl)。

## 3. 描述指纹、方法合同与策略快照分开

完整描述 SHA-256 来自规范化语义描述，用于产物一致性与审计；不是任意业务消息
序列化字节的散列。可兼容字段演进会改变完整描述，不因它不同一律拒绝。
规范化不依赖路径、时间或列表顺序；消息序列化的确定性也不能替代描述规范化。

方法合同包含稳定方法身份、请求/响应类型身份、基数、codec/wire 主版本及必要业务
规则。后续 OPEN 接入必须在业务 work 前核对，错配按 #242 隔离当前 Call；纯正文
解码不冒充这项检查已完成。远端自报合同不提供身份认证或安全授权。

超时、压缩、lane、内存、存储上限和尝试参数放在独立的不可变策略快照；每次 Call
固定其适用策略，不在进行中拼接新旧配置。业务声明的幂等依据与实际重试策略区分，
不根据错误状态推断可以重放；#244 的原期限、提交点及预算要求继续有效。

## 4. 资源策略可以演进，但不能假装已协商

Nanopb 将存储选项与 wire 描述分开，这一点可借鉴。提高生成存储上限可能改变 C
对象/API/内存需求；降低接收上限可能拒绝较大数据，但这些差异分别报告，不能直接
要求更换业务方法 ID。[生成选项](https://github.com/nanopb/nanopb/blob/master/docs/reference.md)

每个解码 profile 始终有有限的输入字节、字段、元素、已知嵌套、未知字段和工作
预算；缺失或不合法配置拒绝创建，不隐式改成无限。有效配置不意味着任何消息都能
被接受；配额耗尽、坏长度及不支持类型须给出不同错误原因，供 RPC adapter 映射。

滚动发布的默认发送 profile 不能超过支持窗口内已知的接收能力；更大内容须取得
明确的对端能力/配置依据，或在本地以资源错误拒绝。不得截断、自动改业务值或重放。
wire 可解析与“所有新值都能被旧配额接受”是不同承诺，验收矩阵分别验证。

项目现有 Channel 已通告消息大小及接收压缩能力，Record 还检查本地方法策略；
它们不是完整的逐方法/逐字段能力协商。复用现有能力前必须验证适用层级，不假称
现有 HELLO 已协商所有 schema 限制。

- 压缩启用不改变类型身份；未确认方法接收能力时维持允许的 NONE 或明确拒绝。
  不能只看到 Channel 支持 Zstd 就假定任意方法都接受。
- lane 是路由策略；当前两端方法要求匹配。未实现协商/双 lane 接受前，换 lane
  不能宣称无中断滚动兼容，但也不把它记作正文类型改变。
- deadline/尝试配置不进入正文类型指纹；仍遵守本 Call 原期限与唯一结果。

项目事实入口：src/transport/protocol/message_caps.h、src/transport/channel/channel.c
与 src/rpc/rpc_record_stream.c；这些代码未因本文改变。

## 5. 验证后发布视图，未知字段可受限往返

借鉴 FlatBuffers 的先验证后访问、SBE 的顺序游标与直接缓冲，以及 Cap’n Proto
对遍历工作的约束。生成代码不默认增加堆分配、线程切换或中间缓冲。
[验证器](https://github.com/google/flatbuffers/blob/master/include/flatbuffers/verifier.h)、
[SBE 原则](https://github.com/aeron-io/simple-binary-encoding/wiki/Design-Principles)、
[遍历限制源码](https://github.com/capnproto/capnproto/blob/master/c%2B%2B/src/capnp/message.h)

C 视图借用不可变源，Rust 用 View<'a> 表达同一寿命；数组使用有界迭代器，不建立
任意对象树。验证字节数、节点/元素工作及已知深度独立受限；重复建立子视图的费用
归属明确，不能重置共享工作预算规避限制。不把低复制表述成 TLS/Zstd 全路径零复制。

未知字段提供两种明确操作：不改字节的 copy_wire，以及显式的有界携带/重编码。
后者在修改已知字段时保留允许的未知内容，拒绝重复 ID/冲突并遵守输出与工作预算。
跨安全域转发须由应用明确选择；逐字段重建对象可能丢失未知内容，文档和测试均
明确这一点，不以整包复制替代升级代理验收。

编码借用到函数返回，调用方提供输出；预检容量/值/重叠，成功才写 written。
解码成功才发布视图，失败不修改业务输出。C/Rust 保持相同错误分类。持有 CallRef
不延长正文借用；后续适配器的异步保存须走明确的持有或有界复制机制。

## 6. wire 候选与选择依据

继续比较两个方向，当前不把未测参数定为生产格式：

| 候选 | 借鉴点与预期收益 | 必须验证的成本 |
|---|---|---|
| 紧凑、可跳过的顺序字段编码 | Protobuf/Thrift 的稳定标签与紧凑表示；稀疏字段、未知字段演进较直接 | 整数边界、重复/排序规则、扫描成本、未知字段重编码 |
| SBE 式固定块加明确演进边界 | 固定数值直接读取、顺序游标、低分配 | 块尾/变长字段限制、缺席表示、旧块边界与未知扩展保留 |

FlatBuffers/Cap’n Proto 提供视图与验证方面的经验，暂不为了“零复制”先引入完整
偏移指针图或跨段对象系统。是否需要随机访问由实际负载决定。

RPC 方法上下文已经包含的类型信息，不未经论证在每条 MESSAGE 完整重发；独立
文件/裸消息封装另定义身份与边界。省略重复信息的前提是方法匹配已实际完成，不能
以未来能力掩盖当前缺少检查。准确 wire 字段、编号和大小在候选对照后定稿。

对照至少覆盖小标量、4/64 KiB 正文、标量数组、嵌套及稀疏字段；记录编码、验证、
顺序/随机读取、未知字段修改往返的字节、CPU、尾延迟、分配/复制和内存。参数、
主机、源码、工具及负结果均保留。[字节算例](../../reviews/custom_message_open_source_lessons_20261029.md)
只证明规格记账，不能替代运行或宣布性能优胜。

[后续形状对照](../../reviews/custom_message_shape_comparison_20261029.md)已覆盖 28 个
Python 参考样例、224 个新旧组合、256 个固定 seed 往返及六个实际负对照。
据此建议通用 RPC 优先收敛紧凑字段，数组采用 packed 固定宽度值；初版保持单一
通用格式，固定块留作高密度数值负载的后续候选。当前固定块验证 CPU 更低的 C
结果仍保留，不以 Python 语义/字节比较宣称 CPU 优胜或端到端性能相同。

未知携带须逐层保留，旧端验证不证明未来语义合法；原字节复制、语义重编码和
规范化字节分别定义。形状对照实际观察到固定块从 v1 重编码为 v2 时字节增长而
语义不变，不能把一般重编码字节当作稳定签名/内容寻址输入。具体 wire 仍待定稿。

## 7. 构建与验收门槛

兼容检查参考 conformity：固定支持基线，分别输出 wire/API/语义/策略差异，生成
漂移和新↔旧双向数据进入构建。基线不由远端提供，不静默少检查一版。
工具人读输出接入现有国际化；生成代码注释使用简体中文，机器键/状态值保持稳定。
Xmake 为构建与测试入口，原 CI 身份、目标参数和超时保持；所有临时文件只在 build/。

wire 定稿后、生产实现之前写分任务计划；实现须实际验证：

- C/Rust 新↔旧请求/响应、缺席/零值/空值、开放枚举、未知字段保留及修改后往返。
- ID 复用、类型/含义改变、语义必要字段变化、仅策略变化的准确分类和拒绝行为。
- 每个截断点、长度/整数溢出、重复/未知字段、深度/工作/未知字段预算耗尽。
- C11/C++11 边界、Rust 借用正反编译、GCC/Clang、ASan/UBSan、无隐藏分配和失败
  输出不变；生成工具的国际化、确定性、漂移及兼容基线。
- 后续 OPEN 前方法匹配、四种基数、取消后迟到结果、同连接健康调用、压缩/预算
  和 Rust Call 所有权矩阵；纯 codec 结果不提前计为这些通过。

当前没有生产 codec、schema 编译器或生成桩实现，未改变公开 SDK 的 11 头安装边界。
本次修订设计并归档独立研究实验；#245 与完整发布目标仍开放。

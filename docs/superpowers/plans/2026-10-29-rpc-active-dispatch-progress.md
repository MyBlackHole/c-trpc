# RPC 活跃调用轮转与有界推进实施计划

关联 #247、#243、#241。执行方式：主会话内联执行，不派发子 agent。

## 依据与不变量

dev.173 的 40k 明文重复性九个样本均不干净；用户态 `cycles:u` 采样中，三个
Server 进程的 dispatch/endpoint pump 自身分别占约 7.39%/6.57%。采样只用于定位，
不作为容量结果。当前 dispatch 固定扫描整个槽位表，Endpoint 每次推进又调用 64 次
单步 pump，空槽会消耗有限推进预算，稀疏调用需跨多次 timer 才再次取得机会。

采用 owner 独占的侵入式活跃槽环：每槽增加两个索引，dispatch 维护活动计数和游标。
仅成功准入插入，仅成功退役移除；终局已通知但未退役的调用仍在环中。
每次 pump 最多处理 min(limit,active_count) 个不同调用；Endpoint 在本轮开始读取
活动数，只处理 min(progress_limit,active_count) 个，再逐步处理原有 deferred 事件。
不增加堆分配、线程或锁；新增固定存储由既有 sizeof/预算预留计算覆盖。
错误和取消不能越过 owner 复核，单调用每步至多一条记录/一次任务提交，失败保留原所有权。

## 试验结论：拒绝候选（2026-10-29）

稀疏推进红测按预期失败；候选实现后六个 RPC/Endpoint/期限/取消/嵌套定向目标通过。
交错 A/B（每轮调整先后顺序，三轮各三个 profile）的成功速率中位数如下：

| profile | 基线 RPC/s | 候选 RPC/s | 候选/基线 |
|---|---:|---:|---:|
| small | 4717.8 | 4995.8 | 1.059 |
| default | 5613.8 | 4892.3 | 0.871 |
| large | 6143.6 | 4795.0 | 0.780 |

两者仍有发生器丢弃/迟到与资源池压力，不能据此作容量声明；数据也不支持保留该优化。
候选把有限扫描额度更多用于活跃调用，改变推进密度，可能增加状态检查和池争用；
这一因果解释仍是推论，不将采样中的热点直接等同于根因。全部生产与测试改动已按
保存的 patch 精确撤销；恢复重建后的 `bench_rpc` SHA-256 与原基线均为
`4b313e99fea989b517fae730c3d475f13ec08a5ca53e69afa20156d5b01c50a1`。
既然候选已被拒绝，不再为它运行全量/消毒器或远端 CI；这不是跳过交付门禁。
原始 JSONL、候选 patch、两个二进制与采样保留在忽略目录 `build/performance-20261029/`。
40k 性能门槛和 #247 保持未完成，后续须重新定位，而非继续堆叠这一方案。

# #249：十二类长期治理的逐项借鉴与执行设计

日期：2026-10-15。性质：长期规则下的执行方案；不是永久 P0 工单，也不是本轮已经完成的月度审查。与 #250 草稿治理文件互补，不改写其历史记录。

## 1. 管理模型与证据范围

采用“规则版本 → 有限任务 → 实现 PR → 精确验证记录 → 后续持续触发”的链。阶段任务关闭后规则仍存在；新缺陷不无限扩张已完成任务。规则、检查工具、检查运行及通过结论分别记状态。

[Google 代码审查](sources.md#s31) 强调持续改善健康；[SLSA provenance](sources.md#s33) 强调构建来源的可追溯描述；[可复现构建](sources.md#s34) 要求固定输入和环境下的产物一致。借鉴证据和流程，不宣称本项目已有 SLSA 级别、可复现认证或任何安全背书。

## 3. 责任与触发矩阵

相关 PR：作者填适用 G 编号、改变的不变量、命令与证据；审阅者核查未覆盖范围。纯文档变更无需无差别重跑所有性能/平台任务，但要检查事实状态、链接、任务范围和来源。

架构里程碑/候选发行：维护负责人汇总未闭环风险、例外和真实支持矩阵；先判断此次发行是否受影响，不因模块化长期存在而全局阻塞。责任人/复核人必须在当次记录写明；现在未指定的角色保持待指定。

活跃维护期月度：依赖与通告、未解释偶发、例外到期、覆盖缺口和债务优先级；严重安全/资源/生命周期问题按风险立即触发。无调度器时只是人工规则，不能说助手会后台持续检查。暂停维护和恢复时的补查也要有记录。

## 4. 依赖安全与许可的具体边界

建议把生成器、CI action、系统包、TLS/压缩库都纳入依赖清单。远端 action 选择经过核查的完整 commit 标识，权限最小化，不能让不可信 PR 代码接触发布凭证。固定版本必须配升级/通告流程，否则固定也会长期保留已知风险。

发行来源记录包含源码、工具链、参数和输入摘要；“有一份 JSON”不等于构建来源真实可信。相同环境可复现、源码审查和漏洞适用性是不同证据，不互相替代。许可检查以实际引入/分发材料和项目政策为准，不能从目录名或 SPDX 一行推断全部分发义务。

## 5. 有限的落地切片

GOV-A：合入经过审阅的治理规则、任务索引和 PR 表单（#250），不关闭实现任务。

GOV-B：建立真实检查登记：rule_id、实现脚本/人工角色、覆盖范围、最近运行、结果、未实现后继任务。先复用已有工具，不为每领域再写一套重复框架。

GOV-C：选择一个真实实现 PR 使用完整记录，检查作者与审阅者能否清楚区分“未执行/失败/不适用”。补缺口而不是勾满模板。

GOV-D：做一次有责任人和范围的里程碑复核，再决定哪些周期项目值得自动化；自动任务的频率/权限/失败反馈单独审查。

阶段记录应有接受标准：不变量、变更范围、已执行验证、残余风险、退出/归档条件。模板填写本身不是工程正确性证据。

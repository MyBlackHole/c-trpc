# c-trpc 代码说明规范

## 语言要求

c-trpc 的所有非代码说明必须使用中文，包括：

- README、设计文档、架构文档、测试说明、基准测试说明和提交说明；
- 公共头文件注释、源文件注释和测试代码注释；
- 架构图中的说明文字、表格标题、章节标题和流程说明；
- 新增内容以及后续重新整理、引用的历史内容。

以下内容属于代码、固定名称或原文，可以保持原样：

- C、C11、POSIX、Linux、epoll、eventfd、pthread 等标准、系统或接口固定名称；
- API、函数名、类型名、变量名、结构体字段、宏、枚举、协议字段和状态值；
- 文件名、目录路径、命令、命令行参数和配置项；
- 外部协议或规范中的固定名称，例如 HELLO、GOAWAY、PING/PONG、CONTROL/BULK；
- 日志、错误信息、工具原始输出以及为了验证而保留的原始测试结果。

概念解释必须使用中文。不要仅因为代码模型使用英文标识符，就在说明文字中继续使用英文概念。例如应写：

```c
/* Endpoint 使用强引用计数保护跨工作线程的异步生命周期。 */
```

而不是：

```c
/* Endpoint uses a strong reference to protect async lifetime across workers. */
```

标识符本身不翻译，也不要为了中文化修改 API、协议字段、状态名或代码结构。

## 注释目标

注释优先说明“为什么”，其次说明“不明显的约束”，不要重复代码本身。

推荐说明：

- 资源由谁创建、当前由谁拥有、何时发生所有权转移；
- 为什么需要引用计数、静默屏障、锁或内存顺序约束；
- 成功和失败路径上的资源归属；
- 生命周期状态转换和销毁顺序；
- 协议约束、兼容性约束和边界条件；
- 不能从代码表面直接看出的并发不变量。

不推荐：

```c
/* i 自增 */
i++;

/* 给 state 赋值 */
state = TR_CONN_ACTIVE;
```

## 资源所有权注释

资源相关 API 应明确说明以下语义之一：

- **借用**：调用方仅临时使用，不接管释放责任；
- **当前拥有**：当前调用方负责后续释放；
- **仅在 TR_OK 时转移所有权**：调用成功后由被调用方负责释放，失败时仍由调用方拥有；
- **强引用**：通过引用计数持有共享生命周期；
- **弱句柄或能力句柄**：句柄本身不代表对象所有权。

推荐格式：

```c
/*
 * 所有权：
 * - TR_OK：Reactor 接管 fd；
 * - 其他返回值：fd 仍由调用方拥有。
 */
```

## 并发注释

并发说明必须尽量明确资源的所有者线程、允许访问的执行上下文以及必要的同步条件。

推荐：

```c
/* 仅 Reactor 所有者线程修改；其他线程通过命令队列提交操作。 */
```

或：

```c
/* 调用前必须已经持有 endpoint->lock。 */
```

如果状态可以通过单线程所有者模型约束，不要用“线程安全”这种模糊表述代替具体的所有权和同步说明。

## 中文与固定名称混排

- 说明句子的主体必须是中文；
- Markdown 中的代码标识符使用反引号；
- C 注释中的代码标识符直接保留原名；
- 固定名称只在确有必要时保留，不把一般技术概念当作必须保留的英文术语；
- 错误码、状态值、API 名称、协议字段和命令保持原样；
- 同一概念在说明中使用统一的中文表达，避免中英文来回切换。

例如：

- 使用“所有权”，不使用英文概念词替代；
- 使用“引用计数”，不使用英文概念词替代；
- 使用“静默屏障”或结合具体语义写“等待回调全部退出”，不直接用英文概念词替代；
- 使用“工作线程”“所有者线程”“命令队列”“回滚”等中文说明；
- 当 `Reactor`、`Channel`、`Call`、`Stream` 是代码中的具体类型、模块或对象名称时可保留原名，但围绕它们的解释必须使用中文。

## 公共头文件

公共头文件注释必须优先说明调用契约：

1. 参数是借用还是发生所有权转移；
2. 返回对象由谁拥有；
3. `TR_OK` 和失败时所有权是否变化；
4. 是否同步等待；
5. 是否允许从 Reactor 回调或工作线程中调用；
6. 是否有线程、生命周期或执行上下文限制。

## 源文件

源文件中的实现注释主要说明：

- 不变量；
- 锁顺序；
- 引用计数生命周期；
- 静默与销毁边界；
- 资源所有权转移；
- 故障恢复和回滚原因；
- 性能路径中为何避免某种操作；
- 单线程所有者与跨线程提交之间的边界。

## 历史内容迁移要求

历史英文说明同样属于中文化范围，不能因为已经存在就继续保留。

处理旧代码或旧文档时：

1. 修改到某个区域时，必须同步清理该区域的英文说明；
2. 专门进行中文化整理时，应覆盖现有 README、docs、公共头文件注释、源文件注释和测试注释；
3. 原始日志、错误输出、测试结果和外部引用原文为了保持证据完整性可以不翻译；
4. 中文化不得改变 API、ABI、协议格式、执行逻辑、测试语义或性能语义。

## 新增内容要求

新增或修改非平凡代码时，新增说明必须使用中文。

评审发现新的英文非代码说明时，应作为规范问题修正，而不是继续扩散到新的文档、补丁或交付包中。

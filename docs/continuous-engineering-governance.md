# 长期工程治理与阶段验收

建立日期：2026-10-15。
长期维护索引：[议题 #249](https://github.com/MyBlackHole/c-trpc/issues/249)。

本文定义持续责任，不是全量代码审计、安全认证或功能完成报告。
规则被记录、规则进入人工审查、自动门禁被实现、某次验收已通过，是四个不同状态。
未实现的检查必须由有限任务追踪，不得因存在本文而宣称已经执行。

## 1. 长期维持原则，分阶段解决问题

模块化、所有权、安全和性能等都需要长期维护；每一阶段的整改仍须有范围和结束条件。

| 对象 | 用途 | 完成与关闭规则 |
|---|---|---|
| 本规范与 #249 | 维护原则、触发条件、证据要求及现有任务索引 | 持续维护；索引可被替代或归档，不计作永久未完成的研发交付 |
| 架构决策记录 | 记录方案、约束、权衡和被替代关系 | 明确提议/接受/被替代；设计接受不等于实现交付 |
| 阶段 issue | 修复具体缺陷或建立一个有限的新能力/边界 | 按约定范围验收，证据齐备后关闭；新问题建立关联任务 |
| 实现 PR | 交付实际变更与测试证据 | 说明受影响治理领域、验证、风险和任务关闭范围 |
| 复核记录 | 记录某个日期/版本/平台上的检查结果 | 一次记录只对其实际范围有效，不能自动沿用于后续版本 |

**关闭阶段任务不关闭治理责任；保持长期规则不要求一个实现任务永远开放。**
不得不断扩大已完成任务，也不得把原验收中的未完成内容转移后伪称全部交付。
范围改变必须明确说明未交付内容、后继任务及批准依据。

正式发布前，以正确性为先，可以在有理由的设计和测试下修改 API、ABI、线协议、
模块职责和旧测试，不为了兼容开发期实现保留无必要的分支。
版本识别、协议不匹配拒绝以及状态描述准确仍是正确性要求。
正式发布后的承诺须另按发布契约管理，不能自动延续任意破坏兼容的政策。

优先级按具体风险决定，而不是按“是否长期工作”决定。
生命期、安全、协议等正确性缺口可为 P0；一般文件拆分、可读性或命名整理
按实际收益安排，不自动成为发行阻塞项。
长期维护不能成为推迟严重缺陷的理由，也不能成为无期限停止功能交付的理由。

## 2. 持续维护清单

下面的 G 编号用于 PR 影响分析和复核记录。
关联议题仅作为阶段入口，其状态应实时核对，不能由本表推定完成。
每个领域都由相关 PR 提交者提供证据，审阅/合并责任人核验；
跨阶段复核由当期维护责任人组织，具体姓名在当期任务中登记。

| 编号与领域 | 触发条件 | 最小检查和证据 | 阶段入口 |
|---|---|---|---|
| G01 模块化与依赖 | 模块、私有布局、导出头/符号、共享工具或跨层调用变化 | 职责和允许依赖；状态唯一修改者；模块替身/隔离测试；边界例外 | #248、#246 |
| G02 所有权、并发与生命周期 | 分配、引用、异步操作、锁/原子、取消、关闭或回滚变化 | 接受/拒绝/释放责任；协议终局、最后回调、资源回收三个屏障；故障交错 | #243、#154 |
| G03 RPC、协议、接口与编码 | 调用状态、基数、元数据、状态码、codec、重试、排空或版本变化 | 状态表与非法序列；双方契约和版本拒绝；无假成功；副作用与重试边界 | #240、#242、#244、#245 |
| G04 资源、背压、公平与活性 | 池、窗口、队列、缓存、任务、分片、压缩或配额变化 | 网络/存储/CPU/任务分域计账；饱和/慢消费者；压力解除后前进；停止收敛 | #241、#235、#154 |
| G05 安全、身份与隐私 | 信任边界、TLS、凭证、压缩、解码、日志或部署入口变化 | 威胁分析、鉴权与恶意输入负向测试；降级/重放/泄密约束；安全失败作用域 | #234、#235、#242、#245 |
| G06 性能与效率 | 热路径、复制/分配、锁、调度、流控、TLS/压缩或默认值变化 | 对等负载/语义/环境下的基线；尾延迟、CPU/RSS、拒绝与完成率；回退说明 | #241、#246、#247 |
| G07 测试、静态分析与证据 | 每次相关变更；工具升级；失败、偶发或告警变化 | 精确提交与配置；正/负例；种子/日志可重放；首个失败保留；告警变化解释 | #247、#154 |
| G08 平台、构建、SDK 与发行 | 工具链、Xmake、内核/架构、安装接口或支持声明变化；发行前 | 真实支持矩阵与编译参数；外部消费端；数据模型边界；未验证范围明示 | #154、#245、#246 |
| G09 依赖、供应链与许可 | 运行时/构建/CI 依赖增删或升级；安全通告；月度复核 | 来源/版本/校验/用途清单；漏洞适用性与更新测试；LICENSE/NOTICE/SPDX 与分发内容 | #234、#235、#154 |
| G10 可观测性与故障定位 | 对象模型、指标/日志变化或难定位故障 | 调用与尝试、网络与解压字节口径；标签有界；隐私；只读快照不泄漏私有状态 | #247、#248 |
| G11 文档、架构决策与示例 | 行为、默认值、能力状态或支持范围变化；里程碑 | 当前/提议/历史分开；契约和示例同步；被替代关系明确；历史原始证据保留 | #239、#238、#248 |
| G12 技术债、回归与维护流程 | 新缺陷、临时例外；里程碑；月度复核 | 有限任务、责任及风险优先级；复核日期；首次失败和残余风险；禁止重跑到绿结案 | #154、#239、#247、#248 |

不得把 G09 的规则存在当作已经做过漏洞扫描，或据此宣称依赖当前安全。
代码可读性、注释与错误处理的日常维护同时适用 G01、G02、G11、G12；
不因它们没有独立的永久任务就免除责任。

## 3. 关键边界的长期要求

### 3.1 模块化

每个组件应有源文件/头/符号归属、窄契约、状态所有者、生命周期责任及验证入口。
目录调整不等于解耦；一个最终静态库也不排斥模块隔离。
合法的组合根可以装配多个模块，不因它依赖多个组件就判错。
库内导出契约和模块私有头须区分，不能只按 `_internal.h` 文件名判断。
编译依赖、符号依赖、运行时回调/所有权图分别检查。
自动门禁应有故意越界的负向测试；尚未实现的边界检查由 #248/#247 追踪。

### 3.2 接受、取消与释放

每个跨模块操作说明输入是借用还是转移、拒绝和接受的提交点、
回调执行域、返回前能否内联回调、取消与正常完成的竞争、失败回滚及最终释放责任。
既有接口可能有不同契约，不能仅为统一外观而假定所有回调行为相同。
改变契约须一并迁移调用方和测试；禁止靠文件搬迁、额外 wrapper 或共享大结构掩盖歧义。
终局已经选定不等于回调结束，更不等于全部存储已可释放。

### 3.3 消息、流控与安全

网络信用、编码/解码存储、工作区、任务/CPU 以及重放缓存分别计账。
存储转移不重复计费，两份存储并存不能漏计；释放解码存储不能混用编码字节返还信用。
允许的消息/窗口组合必须能前进或被明确拒绝，不能永久表现为临时背压。
Message 的压缩输入与 RPC 控制/身份元数据有明确边界，算法、TLS 与 codec 的限制互不替代。
默认 none 不强制引入 payload 复制、工作队列或线程跳转；开启变换后的成本必须验证。
这里定义应维持的性质，不声称当前所有路径已经满足。

### 3.4 证据与回归

每个结论绑定精确 Git 提交、工作树状态、工具/配置/平台及实际命令或工作流。
区分通过、失败、未执行、不适用；缺少环境或跳过不能记录为通过。
PR head 的成功不自动证明合并提交通过；旧提交结果不能代替新提交验收。
仅编译、测试执行、静态分析、负载冒烟、性能实验分别说明，不相互冒充。

首次失败必须保留。相同提交重跑成功可以作为新增证据，但不能单独证明故障原因是环境，
更不能自动将缺陷关闭。临时抑制/隔离需范围、理由、责任人和复核日期。
测试、检查器和告警基线本身也须负向测试；更新基线不能掩盖新增告警或覆盖丢失。
关键结论的摘要、配置及长期可复核结果应进入版本化记录；短期 CI 附件不能作为唯一证据。
不得为了报告整洁删除不利的性能样本或改写历史测试原文。

## 4. 执行触发与责任

**每个相关 PR：**提交者按 G01—G12 分析影响，审阅/合并责任人检查证据。
不受影响的领域允许注明“不适用 + 理由”，不要求每个文档变更执行全性能/跨架构矩阵。
选择的验证强度应由变化风险决定，不能用“改动很小”替代分析。

**每个架构里程碑及候选/正式发行前：**当期维护责任人检查阶段范围、
未闭环的高风险项、自动门禁覆盖、平台和安全声明、例外及历史结论是否仍适用。
发行判断针对具体提交/功能/平台，不要求不存在任何低风险债务。

**活跃维护期每月一次：**当期维护责任人复核依赖与安全通告、偶发失败、
临时忽略/例外、积压债务和近期覆盖缺口。重大安全通告或确定的资源/生命期失效
按风险立即评估，不等待月度复核。暂停维护应留记录，恢复时补查积压。

这些是项目执行约定，不是已经配置的定时任务、通知机器人或助手后台工作。
具体姓名在当期任务/复核记录登记；未指定负责人就标记“待指定”，
不能声称维护已自动执行，也不能捏造个人已接受职责。

## 5. PR 和阶段任务的最小记录

PR 至少包含：目标 issue 和本次范围、适用 G 编号、不变量/接口/所有权变化、
实际验证及未验证项、回退/迁移方案、残余风险、文档和回归维护位置。
纯文档变更也应核查引用、状态和范围，不冒充运行时验证。

阶段任务至少包含：基线、有限范围、责任人、具体风险和优先级、
实现 PR、精确验证提交与结果、残余风险，以及阶段完成后继续维护的规则/测试位置。
跨模块任务按可验收的行为切片交付，不先做没有行为证据的大搬家，也不把边界问题全部推后。

关闭阶段任务必须确认：范围内实现已合入；适用验证完成；契约/示例同步；
没有遗漏原验收内容；确实新增的问题有单独任务；回归与治理规则继续有效。
阶段关闭措辞应是“某一基线、范围或能力已验收”，而不是“模块化/安全/正确性永远完成”。

### 5.1 任务必须先登记、逐项核销（2026-10-20）

对应持续索引 #249 中的执行规则。每项新工作必须先搜索既有 Issue、PR（含 Draft）、分支提交与验收证据，避免复制已完成的工作；复用已有原任务时，不重复新建任务或草稿 PR。

独立任务的唯一编号、范围、基线、前置依赖、不变量、精确验收和完成状态，先写在已有阶段 Issue 或专项台账。当前 RPC V1→V2 清退使用 [#290](https://github.com/MyBlackHole/c-trpc/issues/290)，TSan 故障使用已有 [#289](https://github.com/MyBlackHole/c-trpc/issues/289)。完成一个可独立核验的步骤即勾选并留下对应 SHA、CI/检查结果及仍未满足项；不得等整个阶段结束才笼统补记。

「代码已提交」「本提交自动测试通过」「独立审查完成」「合并 main」「发行验收通过」是不同完成关口。未合并草稿、7/8 作业通过或单次重跑成功，都不能冒充最后一关。受阻事项记失败和原始证据，后续只处理未完成项；阶段收敛后按任务定义关闭并保留关联回归，不删除原始失败历史。

上述是项目的人工/AI 协作约定，仍须在实际任务与 PR 中执行；尚未建立自动判定跨 GitHub Issue 与本地改动的机器人，不把模板条目视作自动门禁。

## 7. 复核和临时例外模板

```text
类型：PR 影响分析 / 阶段验收 / 月度复核 / 发行复核
日期、责任人、复核人（未指定须明示）：
提交/发布版本、平台、工具版本与配置：
适用 G 编号；不适用项及理由：
实际执行内容、命令/工作流/人工核查、证据：
结果：通过 / 失败 / 未执行 / 不适用
问题及关联 issue；风险、优先级和处理责任：
临时例外：精确范围、理由、影响、批准依据、责任人、到期/复核日期：
后续触发条件/复核日期；阶段是否可关闭及理由：
```

例外必须被复核，不允许用宽泛忽略 `src/**`、任意私有头或全部告警替代精确范围。
基线文件不是误报豁免或安全证明；到期不能自动续期。
